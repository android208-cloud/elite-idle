## 1. Контекст и хронология диалога

### 1.1. Цель проекта
Разработка **Elite Idle** — браузерной idle / captain-manager игры по мотивам классической игры **Elite (1984/1985, BBC Micro)** Дэвида Брабена и Яна Белла.

**Ключевой критерий качества:**
- Все механики (генерация 8 галактик, торговля, рынок, параметры кораблей, формулы урона, цены оборудования, правовой статус и боевые ранги) должны строго соответствовать оригинальному ассемблерному коду BBC Micro (репозитории `markmoxon/elite-beebasm` и `elite-source-code-library`) и эталону `txtelite.c` Яна Белла.
- Любое извлечённое значение из оригинала покрывается референсным автотестом.

---

### 1.2. Хронология этапов

#### Этап 1. Базовая реализация игры
1. Создан детерминированный генератор псевдослучайных чисел (Mulberry32 PRNG) для стабильности вселенной.
2. Реализована процедурная генерация 8 галактик по 256 звездных систем с аутентичными названиями, координатами и характеристиками.
3. Построена экономика и рынок 17 оригинальных товаров с детерминированными колебаниями цен.
4. Разработан модуль кораблей, оборудования и пошагового боя.
5. Создано состояние игры (`GameState`), полёты в реальном времени, офлайн-досчёт прогресса, система сохранения v2 в `localStorage`.
6. Реализован веб-интерфейс на чистом TypeScript/CSS с интерактивной картой галактики (Canvas API), вкладками «Корабль», «Карта», «Рынок», «Ангар», «Журнал» и экраном пошагового боя.

#### Этап 2. Сверка с оригинальными ассемблерными исходниками
1. Загружены и подключены эталонные библиотеки:
   - `reference/txtelite.c` (эталон Яна Белла)
   - `reference/elite-source-code-bbc-micro-cassette-main/`
   - `reference/elite-source-code-library-main/` (полный аннотированный архив исходников)
2. Создан скрипт `tools/extract-ships.ts`, автоматически парсящий таблицы чертежей кораблей из оригинального ASM-кода (`ship_*.asm`).
3. Заменены все первоначально приблизительные значения:
   - Энергия, щиты, лазеры, ракеты и награды кораблей.
   - Цены оборудования по таблице `PRXS`.
   - Пороги рангов по анализу подпрограммы `STATUS` (`status.asm`).
   - Механика урона противников по формуле `byte#19 >> 1` из `tactics_part_6_of_7.asm`.
4. Написан набор эталонных тестов `test/reference-ships.test.ts` (26 тестов), сверяющий каждый корабль и предмет с оригиналом. Общее количество тестов доведено до 71/71.

#### Этап 3. Публикация на GitHub и настройка CI/CD
1. Настроен `.gitignore` (исключены `node_modules`, `dist` и 23 МБ эталонных архивов `reference/`).
2. Оформлен подробный `README.md`.
3. Репозиторий опубликован на GitHub: `https://github.com/android208-cloud/elite-idle.git`.
4. Создан GitHub Actions workflow (`.github/workflows/deploy.yml`) для сборки, тестирования и деплоя на GitHub Pages.

## 2. Принятые архитектурные решения

### 2.1. Парадигма кода
- **Функциональный подход и иммутабельность:** функции ядра (`buy`, `sell`, `refuel`, `startJump`, `advance`, `combatRound`, `combatAction`) принимают состояние и возвращают новое, никогда не мутируя входной объект.
- **Отсутствие сторонних UI-фреймворков:** проект собран на легковесном стеке Vite + TypeScript + Native DOM API без React/Vue, что обеспечивает мгновенную загрузку (< 40 КБ JS).
- **Разделение слоев:** ядро (`src/core/`) полностью изолировано от DOM и браузерных API, что позволяет запускать все тесты в чистом Node.js окружении без эмуляции браузера.

### 2.2. Единицы измерения
- **Деньги:** целочисленные десятые доли кредита (`100 = 10.0 CR`, `1 = 0.1 CR`). Это исключает ошибки округления с плавающей точкой IEEE 754 и в точности соответствует `txtelite.c`.
- **Топливо и расстояния:** десятые доли светового года (`70 = 7.0 LY`, максимальный бак Cobra Mk III = 70).
- **Время в пути:** рассчитывается из расстояния и темпа игры (`settings.speed`). Поддерживается фоновый офлайн-досчёт при открытии вкладки.

### 2.3. Игровая механика и математика из оригинала

#### Экономика и галактика
- **Алгоритм Фибоначчи для галактики:** три 16-битных числа (`w0, w1, w2`) генерируют имя, координаты, тип экономики, форму правления и техуровень каждой системы.
- **Цены рынка:** базовая цена, экономический градиент, плюс случайное колебание от `fluctuation` системы.

#### Модель боя и урона
- **Урон врага по игроку:** рассчитывается по байту конфигурации вооружения корабля `byte#19`:
  $$\text{Damage} = \text{byte\#19} \gg 1 = ((\text{laserPower} \ll 3) \mid \text{missiles}) \gg 1$$
- **Лазеры игрока** (из `elite-source-docked.asm`):
  - Импульсный (Pulse): $\text{POW} = 15$
  - Добывающий (Mining): $\text{Mlas} = 50$
  - Лучевой (Beam): $\text{POW} \mid 32 = 47$
  - Военный (Military): $\lfloor 128.5 + 1.5 \times \text{POW} \rfloor = 151$
- **Щиты и энергия:** щиты 0–255 (адаптировано в единый буфер), энергия 0–255. Урон сначала поглощается щитами, излишек переходит в энергию.

#### Цены оборудования (таблица `PRXS`)
- Ракета: 30.0 CR (300)
- Увеличенный трюм: 400.0 CR (4000)
- ECM: 600.0 CR (6000)
- Импульсный лазер: 400.0 CR (4000)
- Лучевой лазер: 1000.0 CR (10000)
- Топливосборщик: 525.0 CR (5250)
- Спасательная капсула: 1000.0 CR (10000)
- Энергобомба: 900.0 CR (9000)
- Доп. энергоблок: 1500.0 CR (15000)
- Стыковочный компьютер: 1000.0 CR (10000) *(исправлено: было 15000)*
- Галактический гипердвигатель: 5000.0 CR (50000)
- Военный лазер: 6000.0 CR (60000)
- Добывающий лазер: 800.0 CR (8000)

#### Система рангов (`status.asm`)
16-битный счетчик убийств `TALLY`:
- **Безобидный (Harmless):** 0–3
- **Почти безобидный (Mostly Harmless):** 4–15
- **Слабый (Poor):** 16–31
- **Средний (Average):** 32–63
- **Выше среднего (Above Average):** 64–127
- **Опытный (Competent):** 128–511
- **Опасный (Dangerous):** 512–2559
- **Смертельный (Deadly):** 2560–6399
- **ЭЛИТА (Elite):** 6400+

#### Правовой статус (`FIST`)
- $0$: Чист (Clean)
- $1 \dots 49$: Нарушитель (Offender)
- $\ge 50$: Беглец (Fugitive)
- При каждом гиперпрыжке статус делится на два (`LSR FIST`, `solar.asm`).
- Уничтожение полицейского (Viper) накладывает `ORA #64` — мгновенный статус Беглеца.

#### Этап 4. Стабилизация и аудит против оригинала

1. **Исправлен CI:** деплой на GitHub Pages падал на шаге `Run tests`, потому что
   `node --test test/` на Node 22 пытается загрузить каталог как модуль. Скрипт заменён
   на `node --test "test/**/*.test.ts"`.
2. **Исправлен dev-сервер для превью:** в `vite.config.ts` добавлены `server.host`,
   `allowedHosts` (иначе Vite отвечает 403 на внешний host превью) и аналогичные
   настройки для `preview`.
3. **Исправлен баг паузы ручного боя.** Раньше прибытие сдвигалось на всё календарное
   время от начала боя до хода игрока: ушёл на 3 часа — полёт отложился на 3 часа.
   Теперь в `ActiveCombat` есть `pausedMs`, который копит **только** время, реально
   прошедшее онлайн (это делает `advance`), а офлайн-разрыв при загрузке полёт не
   откладывает. Совместимость со старыми сохранениями v2 обеспечена в `deserialize`.
4. **Добавлен `test/invariants.test.ts`** — прогонные тесты-инварианты на 32 случайных
   сессиях: деньги, трюм, топливо, рынок, RNG, независимость досчёта от разбиения на
   вызовы, идемпотентность `advance`, обратимость сохранений. Именно этот harness
   поймал баг паузы.
5. **Аудит сверки с оригиналом** (`elite-beebasm`, клонируется локально в `reference/`,
   в Git не попадает). Уточнены факты для следующего этапа:
   - **Контрабанда** (`TT110` → `BAD`): `A = (QQ20+3 + QQ20+6) * 2 + QQ20+10`, затем
     `FIST = FIST OR A` — именно **побитовое ИЛИ**, а не сложение. Проверка выполняется
     при взлёте, а не при посадке.
   - **Оборудование** (`EQSHP`) — **исправлено, см. этап 5**. Проверенные факты:
     - `QQ25 = min(tek + 3, 14)` для версии с диска и enhanced-версий;
       в кассетной/Electron-версии было `min(tek + 3, 12)`, поэтому там нет
       военного и добывающего лазеров (*«this version of Elite doesn't have
       military lasers»* относится именно к кассетной версии).
     - `PRXS` содержит 11 общих покупок + 2 лазера в enhanced-версиях:
       цены `EQUW 60000` → **6000.0 Cr** (военный) и `EQUW 8000` → **800.0 Cr**
       (добывающий). Цены в проекте изначально были верны.
     - `XX13` — **экранный** номер: 1 = FUEL, 2 = ракета, 3 = трюм, … 13 = военный,
       14 = добывающий. Цена читается как `prx-3(XX13) = PRXS[XX13-1]`, а `PRXS[0]`
       — топливо. Предмет доступен при `texNumber ≤ QQ25`, т.е. `tek ≥ номер − 3`.
   - **Продажа** (`TT210`): продаётся **вся партия целиком** по текущей цене и без
     обратного пополнения `AVL` — в idle-версии имеет смысл сохранить это для
     аутентичности.

#### Этап 7. Спавн кораблей и баг Moray

**Баг.** `main_game_loop_part_4_of_6.asm`, ветка одинокого охотника:

```
AND #3      \ A = 0..3
ADC #CYL2   \ CYL2 = 24 → диапазон 24..27
```

По таблице `XX21` номера 24–27 — это Cobra Mk III (пират), Asp Mk II,
Python (пират) и Fer-de-lance. **Moray — номер 28**, то есть ровно за верхней
границей диапазона, и никакой другой код его не спавнит. Комментарий
Марка Моксона подтверждает: *«this means the Moray is never seen in Elite»*.
Оговорка: баг относится к disc/enhanced версиям; в кассетной версии диапазон
логики другой, и там Moray тоже не появляется.

**Решение — исправление Моксона (`LSR A`).** Вставленная перед `AND #3`
команда `LSR A` делает диапазон 24..28. Важная деталь, которую Моксон
описывает как «random», но не уточняет: `LSR A` кладёт младший бит в флаг
переноса, `AND #3` его не меняет, а `ADC #CYL2` прибавляет — поэтому
распределение не равномерное, а **1:2:2:2:1**:

| Чертёж | Корабль | Доля |
|---|---|---|
| 24 | Cobra Mk III (пират) | 12.5% |
| 25 | Asp Mk II | 25% |
| 26 | Python (пират) | 25% |
| 27 | Fer-de-lance | 25% |
| **28** | **Moray** | **12.5%** |

**Вторая находка.** По `e_per_cent.asm` Moray помечен `%00001100` =
Hostile + **pirate**, то есть спавниться должен в *группах* пиратов (`mt1`),
где диапазон `(A AND T) AND #7 + PACK` = 17..24 — там его тоже нет.
Реализовано:
1. `src/core/spawn.ts` — таблицы `XX21` (`PIRATE_BLUEPRINTS`,
   `LONE_HUNTER_BLUEPRINTS`), `moxonLoneHunter()` и `pirateFromGroup()`.
2. `state.ts`: роль `hunter` теперь использует исправление Моксона, роль
   `pirate` — групповую таблицу оригинала с её скошенным распределением
   (Sidewinder 42%, Cobra Mk III 1.6%).
3. Moray доступен с 16 убийств (как Mamba/Krait), а не с 24. `minKills` —
   наше дополнение, в оригинале порогов нет.
4. Worm (чертёж 23) в проекте отсутствует как противник; при его выпадении
   подставляется Sidewinder. Это единственное сознательное отступление.
5. Тест `test/reference-spawn.test.ts` (11 тестов): распределение 1:2:2:2:1
   на всех 256 значениях, недостижимость Moray в оригинале, распределение
   группы, отсутствие Moray среди групповых пиратов.

#### Этап 8. Галактический гиперпрыжок (Ghy + TT111)

Реализовано строго по `common/main/subroutine/ghy.asm`:

## 6. Исправление: настройка «темп игры» не работала

**Симптом.** Смена темпа в настройках не влияла на уже начатый прыжок: полёт,
стартовавший при ×1, прибывал через свои 15 минут при любом темпе.

**Причина — две независимые ошибки.**

1. `Flight.arriveAt` фиксировался один раз в `startJump` как абсолютный момент,
   а `advance()` темп вообще не читал. Поэтому ускорение действовало только на
   прыжки, начатые **после** смены настройки.
2. Смена настройки вызывала полный `render()` через `innerHTML`, который
   уничтожал `#flight-bar`/`#flight-eta`; `updateFlight()` тихо выходил по
   `if (f && bar && eta)`, и прогресс-бар замирал. Казалось, что «нет эффекта».

**Решение.** Истина теперь хранится в «базовых» миллисекундах (при `speed = 1`):
`remainingBaseMs`, `elapsedBaseMs`; `arriveAt` — производное поле, которое
пересчитывается из остатка по текущему темпу. Добавлены `baseToReal()`,
`nextEncounterAt()`, `syncFlightToSpeed()`.

Ключевой момент — где именно применяется темп. Синхронизировать полёт «сразу к
`now`» нельзя: тогда при досчёте одним вызовом (свёрнутая вкладка, длинная
пауза) встречи посреди интервала терялись бы. Поэтому основной цикл `advance()`
подводит полёт **точно к моменту ближайшего события** (`t = min(arrive, enc,
spawn)`), разбирает его, и только после цикла подтягивает остаток к `now`.

Встречи (`pending`) хранятся в базовой шкале **от вылета**, поэтому при смене
темпа они наступают раньше или позже вместе с прибытием и не «съедаются»
синхронизацией.

Пауза боя сдвигает `dueAt` и `arriveAt` на реальный простой; `pending` при этом
не трогается — он живёт в базовой шкале от `departAt`.

**Совместимость.** Старые сохранения (полёт без новых полей) мигрируют в
`deserialize()`: остаток восстанавливается из `arriveAt - departAt`, встречи
переводятся в базовую шкалу. Покрыто тестом.

**UI.** `tick()` больше не делает полный `render()` ради движения полёта: экран
перестраивается только при событиях и структурных изменениях (полёт
начался/закончился, бой, встреча, смена системы), иначе обновляется один
прогресс-бар. Запись в `localStorage` — не чаще раза в 10 с (при событиях —
всегда). Смена темпа в настройках применяется немедленно, не дожидаясь тика.

**Верность оригиналу.** Темп — настройка интерфейса, в оригинальном Elite её
нет (там время полёта задаётся `TT110` и не масштабируется). Механика прыжка,
встреч и боёв не изменилась: темп лишь линейно масштабирует реальные интервалы,
сохраняя все базовые величины.

**Регрессия.** `test/speed.test.ts` — 10 тестов: ускорение и замедление на ходу,
независимость от дробления вызовов, сохранение и миграция старых сохранений.

## 7. Сделано: лимит 200 в `tnpr`

**Статус: исправлено, покрыто `test/reference-cargo.test.ts` (11 тестов).**

**Обнаружено** при разборе вопроса «`HOLD_EXTENDED = 35` против `CRGO = 37`»

**Суть.** В оригинале `tnpr` (`elite-source.asm:17449`) делит товары на две ветки:

```asm
 LDX #12

```

- индексы **13–16** — лимит **200 штук каждого вида** (`CMP #200`),

1. `isTonnes()` (`src/core/state.ts:224`) смотрит только `unit === 0`.
2. **Лимита 200 нет вообще** — золото и камни покупаются без ограничения.
3. `COMMODITIES[16]` («Предметы пришельцев») помечен `unit: 0`, то есть

**Что нужно сделать.**

- Ввести проверку «сколько ещё влезет» по образцу `tnpr`: для индексов 13–16
  `cargo[i] + amount <= 200`, для остальных — по свободному тоннажу.
- Исправить единицу измерения для «Предметов пришельцев».
- Покрыть референсным тестом рядом с `test/reference-*.test.ts`.

**Как сделано.**

- В `src/core/state.ts` появилась `cargoRoom(state, index)` — прямой аналог
  `tnpr`: для индексов 0–12 свободный тоннаж, для 13–16 — `200 - cargo[i]`.
- `cargoTons()` тоже переведён на индексную ветку (`cargoTonsOf`).

**Важная тонкость.** Единица измерения для показа и ветка лимита — разные
вещи. «Предметы пришельцев» печатаются в тоннах (`ITEM 53, 15, 't', 192`),

Поэтому `unit: 0` у них **оставлен как есть** — это верно для отображения,

**Ошибка в моём прошлом анализе (исправлена).** В предыдущем ответе я

Это неверно: `QQ23` печатает их в тоннах, и `unit: 0` соответствует
оригиналу. Проблема была только в отсутствии лимита 200 и в том, что ветка
определялась по единице, а не по индексу.

**Что осталось за рамками (внесено в бэклог, пункты 7–8).**

Сбор груза (`slvy2` в оригинале) вызывает `tnpr`, и там же определяется
содержимое контейнера:

```asm
 LDA #3                 \ спас-под → рабы (индекс 3)
 CPX #TGL
 BCC oily
 BNE slvy2
 LDA #16                \ Thargon → артефакты (индекс 16)
 BNE slvy2
.oily
```

У нас в двух местах (`spawnEncounter` для дрейфующего контейнера и
обработка победы в бою) стоит `Math.floor(dice.next() * 16)` — то есть

При этом ограничение при сборе теперь идёт через `cargoRoom`, что

### Ложная тревога: `HOLD_EXTENDED = 35` против `CRGO = 37`

`CRGO` хранит ёмкость **со смещением +2**, это прямо сказано у Моксона
(`elite-source.asm:17493`): «22 for the standard 20-tonne bay, and 37 for the
large 35-tonne bay». Смещение нужно, потому что `tnpr` сравнивает `a+1 < c+2`.

Инициализация `EQUB 22 + (15 AND Q%)` при `Q% = _MAX_COMMANDER = FALSE` даёт
22 → 20 тонн. Значит 37 → 35. **Наши константы верны, править нечего.**

## 9. Методологическая находка: сверялись не с тем исходником

**Это важнее любой отдельной правки — читать перед любой сверкой с оригиналом.**

`reference/elite-beebasm` — это **кассетная** версия BBC Micro (в её `README.md`:
«Annotated source code for the BBC Micro cassette version of Elite»). В ней
нет военного и добывающего лазеров, а `QQ25` ограничен 12.

Мы же осознанно следуем **disc/enhanced** версии (`QQ25_MAX = 14`, лазеры
`military`/`mining` присутствуют). Значит кассетный исходник — **не тот
эталон**, с которым надо сверять спорные места.

**Правильный эталон** — `reference/elite-source-code-library`:

- `versions/disc/` — исходники дисковой версии, в том числе
  `elite-source-docked.asm` и `elite-source-flight.asm`
  (именно на них ссылается наш `src/core/combat.ts`!);
- `library/common/` — общие подпрограммы с ветвлением по версиям
  (`_CASSETTE_VERSION`, `_DISC_DOCKED`, `_6502SP_VERSION`, …).

**Как проверять выбор версии.** Искать в `library/common/**.asm` конструкцию
`IF _CASSETTE_VERSION OR …: … ELIF _6502SP_VERSION OR _DISC_DOCKED …` и
брать ветку, в которую входит `_DISC_DOCKED`.

**Что это подтвердило (расхождений нет).**

| Место | Кассета | Disc/enhanced | У нас |
|---|---|---|---|
| `POW` (импульсный) | 15 | 15 | 15 ✓ |
| Луч (`POW+128`, биты 0–6) | 15 | 15 | 47 — см. ниже |
| `Mlas` (добывающий) | нет | **50** | 50 ✓ |
| `Armlas` (военный) | нет | `INT(128.5+1.5*15)` = 151 | 151 ✓ |
| `EQSHP`: смещение по теку | `ADC #3` | `ADC #3` | 3 ✓ |
| `EQSHP`: предел `QQ25` | 12 | **14** | 14 ✓ |

`combat.ts` ссылается на `elite-source-docked.asm` — файл, существующий
только в disc-версии, так что ссылка была верной; просто он лежал не в том
репозитории, который мы склонировали первым.

**Отдельно про луч (beam) — оказалось настоящим багом, исправлено.**

Байт `LASER` — это НЕ мощность. Мощность — его биты 0–6:

```asm
main_flight_loop_part_3_of_16.asm:
 PHA                    \ байт LASER текущего вида
 AND #%01111111         \ LAS = биты 0-6 (бит 7 = «луч, а не импульс»)
 STA LAS
```

| Лазер | Байт `LASER` | Сила удара (`& 127`) | Было у нас |
|---|---|---|---|
| импульсный | `POW` = 15 | **15** | 15 ✓ |
| луч | `POW+128` = 143 | **15** | 47 ✗ |
| военный | `Armlas` = 151 | **23** | 151 ✗ |
| добывающий | `Mlas` = 50 | **50** | 50 ✓ |

Независимое подтверждение из оригинала: `CMP #(Armlas AND 127)` — автор
сравнивает силу удара с **23**, а не с 151. Если бы сила была 151, это
сравнение не сработало бы никогда.

Урон применяется так: `LDA INWK+35 : SEC : SBC LAS` — энергия цели минус
сила удара.

**Следствие для баланса.** Луч и импульсный теперь одинаковы по урону за
выстрел — так и в оригинале: луч отличается не силой, а тем, что он
«непрерывный» (`LASCT = 0` против пульсаций у импульсного). Наша модель
«один выстрел в раунд» этого различия не воспроизводит, и это остаётся
осознанной адаптацией; сила удара при этом теперь верная.

Покрыто `test/reference-laser.test.ts` (14 тестов).

## 10. Сделано: темп огня лазеров (LASCT + перегрев)

**Задача.** Раньше все лазеры стреляли один раз за раунд, поэтому луч и
импульсный были неотличимы по урону. Пользователь решил: воспроизводить
темп, как в оригинале.

### Механика: две половины, и вторая критична

**Первая половина — счётчик `LASCT`.**
`main_flight_loop_part_3_of_16.asm`: стреляем только при `LASCT == 0`, иначе
декремент. После выстрела `LASCT = 0` у лазеров с битом 7 (луч, военный),
иначе `LASCT = power & %11111010`. `irq1.asm`: декремент на каждый VSYNC
(50 Гц).

**Вторая половина — перегрев `GNTMP`.**
`lasli.asm`: `GNTMP += 8` за выстрел. `main_game_loop_part_5_of_6.asm`:
`DEC GNTMP` за проход. `main_flight_loop_part_3_of_16.asm`: при `GNTMP >= 242`
стрелять нельзя.

**Почему без перегрева нельзя было обойтись.** У луча и военного `LASCT = 0`
постоянно, и по одному счётчику они стреляли бы 50 раз в секунду — в **10 раз**
чаще импульсного. Именно перегрев приводит темп к реальному. Я едва не
выпустил версию без него: цифры были бы x10, что сломало бы баланс.

### Итог (импульсный = 1)

| Лазер | Урон | `LASCT` | Темп | Отн. | DPS (65%) |
|---|---|---|---|---|---|
| импульсный | 15 | 10 | 4.55/сек | ×1.00 | 44 |
| луч | 15 | 0 | 6.30/сек | ×1.39 | 61 |
| военный | 23 | 0 | 6.30/сек | ×1.39 | 94 |
| добывающий | 50 | 50 | 0.98/сек | ×0.22 | 32 |

Порядок по урону в секунду: нет < добывающий < импульсный < луч < военный —
как и задумано в оригинале (военный сильнее всех, добывающий — инструмент,
а не оружие).

### Реализация

`LASER_RATE` в `combat.ts` — не «прикидка», а симуляция того же контура
(LASCT + перегрев, 50 Гц, 600 секунд), выполненная один раз при загрузке
модуля. Так значения остаются выводимыми из констант оригинала, а не
вписанными руками.

В раунде боя лазер делает `LASER_RATE[тип] / LASER_RATE.pulse` выстрелов;
дробная часть разыгрывается вероятностно (у добывающего 0.22 выстрела за
раунд не должно округляться в ноль навсегда).

Покрыто `test/reference-laser-rate.test.ts` (11 тестов). Всего 166/167.

**Замечание о маске `& %11111010`.** У наших значений она ничего не меняет
(у добывающего 50 = %00110010 младший бит уже нулевой), но она важна как
часть механики и оставлена в коде. В первой версии комментария я ошибочно
написал, что маска даёт 48 — это была ошибка счёта, исправлено.
## 11. КОНЦЕПЦИЯ ИГРЫ (обсуждается, код не пишется)

Раздел ведём вместе с пользователем. Правки сюда вносим по мере решений.

### 11.1. Зачем всё это

**Исходная мотивация пользователя:** вернуть удовольствие от игры детства, но
**без утомительных полётов и боёв в космосе**. При этом космос — значительная и
интересная часть Elite, и его тоже хочется реализовать, но в упрощённом виде.
Как именно — решаем по ходу.

**Следствия (согласовано):**

- мы **не следуем оригиналу на 100 %**; небольшие отступления ради удобства
  допустимы и не требуют «искусственных» обоснований;
- при этом всё, что берём из оригинала, берём точно (см. раздел 9 про выбор
  версии: эталон — `versions/disc` в `elite-source-code-library`);
- приоритет — **не внимание игрока, а прогресс**. Игра должна двигаться, пока
  её не смотрят, и не требовать постоянного клика.

### 11.2. Баг «прыжок во время стыковки» — вариант Б

**Решение:** воспроизводим баг намеренно, как игровую механику (не как
случайный сбой).

**Механика (уточнена по ходу обсуждения):**

| Действие | Топливо | Двигатель |
|---|---|---|
| Обычный прыжок (без бага) | тратится | — |
| Обычный прыжок **с багом из дока** | тратится | — |
| Галактический двигатель **с багом из дока** | **не тратится** | **сгорает** |

**Ключевая находка (идея агента, принята пользователем):** баг из дока даёт
прыгнуть **дальше бака**, а не просто сэкономить топливо.

Почему это нужно: по числам экономики «сэкономить топливо» бессмысленно —
полный бак стоит 14 CR, а галактический двигатель 5000 CR. Экономить 14 CR,
сжигая 5000 CR, — не обмен. А **дальность** (прыжок за пределы 7 св. лет) —
ценность, за которую платить не жалко.

Здесь мы **сознательно отступаем от оригинала**: в оригинале баг не расширял
дальность (топливо всё равно списывалось в `TT18`). Отступление принято ради
того, чтобы механика имела смысл в idle-игре.

### 11.3. Окончательный тупик — открытый вопрос

Проверено на коде: при `топливо = 0`, `деньги = 0`, пустом трюме игра встаёт
навсегда — дохода нет, заправиться не на что, прыгнуть нечем.

В оригинале это не тупик (можно лететь и торговать). У нас — фатально, потому
что в idle игрок просто закроет вкладку.

**Решения пока нет.** Варианты для обсуждения:

- пассивный доход на станции (медленный, но никогда не ноль);
- минимальная заправка «в долг» с долгом;
- бесплатный аварийный прыжок к ближайшей системе;
- осознанная сложность с рестартом (маловероятно для idle).

### 11.4. Космос как окно кабины — направление (обсуждается)

Пользователь предложил: сделать космос отдельным **окном**, как сейчас карта,
но с **видом из кабины**. Плюс вопрос: можно ли упростить пилотирование.

**Текущее состояние UI:** карта уже рисуется на `<canvas id="map">` в отдельной
вкладке (`TABS` → `map`, `drawMap()`). Значит кабина ляжет в ту же схему:
ещё одна вкладка + собственный `drawCockpit()` на canvas.

**Ключевой принцип, который стоит зафиксировать:** пилотирование не должно
быть обязательным условием прогресса. Если игрок не трогает управление, полёт
всё равно завершается (сейчас так и работает — таймер идёт сам). Кабина должна
давать **преимущество**, а не требовать присутствия.

Кандидаты на «упрощённое пилотирование» (обсуждается, не решено):

- удержание курса: одна кнопка/ползунок «держать цель», без свободного
  управления;
- автостыковка при наличии стыковочного компьютера (`dockingComputer` у нас
  куплен, но ничего не делает — это готовый кандидат);
- ручное управление только для уклонения от встреч, как опция для желающих;
- вид из кабины как **индикатор** (куда летим, сколько осталось, что рядом), а
  не как способ управления.

### 11.5. Что пока не решено

- бой: пошаговый на 60 раундов слишком «дорогой» по вниманию; вариант —
  авто-бой с настройкой агрессивности, ручной как опция;
- нужен ли вообще свободный полёт, или только «прыжок + прибытие»;
- роль стыковочного компьютера (сейчас не реализован).

## 12. СЕКРЕТНЫЕ МИССИИ: что подтверждено кодом ZX Spectrum

Источник — дизассемблер **ZX Spectrum** `Rasmus-M/elite-skoolkit`
(`reference/elite-zx-skoolkit/src/elite.skool`, 1785 файлов).
Библиотека Моксона покрывает **только BBC Micro** и для вопросов о Spectrum
непригодна — см. раздел 9.

### 12.1. Методологическая заметка

Первая попытка поискать миссии сделала вывод «миссий нет» по библиотеке
Моксона. **Это был неверный вывод**: он верен только для BBC Micro.
В ZX Spectrum миссии есть — и они подтверждаются дословно.

Правило на будущее: **«нет в библиотеке Моксона» ≠ «нет в оригинале».**
Вопрос «есть ли X в Elite» требует указания версии.

### 12.2. Миссия «Сверхновая» — подтверждена полностью

Все токены найдены в коде ZX Spectrum:

| Строка | Токен | Адрес |
|---|---|---|
| `MAYDAY * CORIOLIS IN DANGER *` | `$22` | F210 |
| `FUEL LEAK*` | `$91` | F4EB |
| `THE SUN IS GOING NOVA… WILL YOU SAVE US (Y/N)?` | `$5A` | F7C0 |
| `REFUGEES` | `$0B` | — |
| `GEM-STONES` | `$3F` | — |

**Логика в коде (это важнее самих строк):**

- **`D0B0` — mission_flags**, «порт BBC-шного `TP`». Перегружен битами:
  - **бит 7** — миссия принята (`paint_confirm_screen`);
  - **бит 5** — миссия завершена, ставится на торговом экране
    (`buy_cargo`, путь продажи/доставки);
  - **бит 6** — подбор спецгруза `$FF`, ворота для экранного мерцания;
  - **бит 3** — экран события показан.
- **`D0AF` — arrival_state**, состояние прибытия после гиперпрыжка.
  - **значение 4** — прибытие **в разгар миссии**;
  - **значение 5** — особый экран (`resume_screen_after_load`).
- Пока **бит 7 установлен И `arrival_state = 4`**, игра **отключает боевой ИИ
  и обработку E.C.M.** (`A3AB`, `B7F7`) — потому что на борту беженцы.
- **`7222`** — экранное мерцание по клавише Y, срабатывает **только пока
  везёте** спецгруз.
- **`D138 paint_confirm_screen`** — тот самый экран «(Y/N)?», выставляет бит 7.

**Сценарий:** гиперпрыжок → красный экран + `FUEL LEAK` → `MAYDAY CORIOLIS IN
DANGER` → успеть состыковаться → клавиша покупки груза → вопрос про сверхновую
→ Yes → беженцы в трюм (`REFUGEES`, бит 7) → немедленный прыжок → на другой
станции Sell → **100 g gem-stones**.

**Не восстановлено:** точная арифметика начисления награды (100 г камней).
Структура понятна, конкретная инструкция — нет.

### 12.3. Миссия «Констриктор» — в ZX Spectrum ОТСУТСТВУЕТ

Проверено перебором: `constrictor` и `CONSTRICTOR` — **0 совпадений** по всему
`elite.skool`. Планеты `REESDICE` тоже **0**. В списке кораблей
(`ship_*`) тоже нет.

При этом в BBC-версиях Constrictor **есть** (6502sp, apple, c64 —
`library/enhanced/main/variable/ship_constrictor.asm`).

**Вывод (уточнён):** в дизассемблере `Rasmus-M/elite-skoolkit` — **48K-версия**
(снапшот `elite.z80` = 43794 байта, все адреса ≤ `$DFFF`, банков нет).
Constrictor — миссия **128K-версии ZX Spectrum**. Отсюда 0 совпадений.

**Значит вывод «Constrictor'а нет в Spectrum» — НЕВЕРЕН.** Он есть, но в другой
версии того же компьютера. Наш дизассемблер эту версию не покрывает.
Подробно — раздел 13.

### 12.4. Таргоидские миссии — есть, но урезаны

В коде найдены:
- `Token $C4: MISSION` — общее слово;
- `Token $DD` — сообщение статуса таргоидского вторжения;
- `Token $DE` — вербовка на спецмиссию («…BY G… COP: …»);
- `Token $DF` — брифинг перед станцией Таргоидов (по обрывкам:
  «…S… E…, A NEW INVASION… REPAIR… VASION… TAKE… WILL NEVER… GOOD LUCK»);
- `THARGON`/`THARGOID` — 17 упоминаний, корабли `ship_thargon`,
  `ship_thargoid` в списке.

**То есть таргоидская ветка в Spectrum реально есть** — не только слухи.

### 12.5. Невидимость и глушитель E.C.M. — ВАЖНОЕ РАСХОЖДЕНИЕ

Вы упомянули, что в награду дают **Cloaking Device** и **ECM Jammer**.
Код говорит иное:

**1. Невидимость (`CLOAKING DEVICE`, токен `$7D`) — в игре есть, но в
магазине её НЕТ.**
Список покупок строго 14 предметов (`equip_ship` @ `$E973`): FUEL, MISSILE,
LARGE CARGO BAY, E.C.M.SYSTEM, EXTRA PULSE LASERS, EXTRA BEAM LASERS,
FUEL SCOOPS, ESCAPE POD, ENERGY BOMB, ENERGY UNIT, DOCKING COMPUTERS,
GALACTIC HYPERSPACE, MILITARY LASER, MINING LASER.
Совпадает с BBC-шным `EQSHP` один в один. `CLOAKING DEVICE` там нет.

Где она используется:
- **`$D183 record_special_pickup`** — при подборе объекта типа `$FF`:
  ставит **бит 6** mission_flags, **повышает боевой ранг** (`INC $D062`),
  печатает на приборной панели **«CLOAKING DEVICE»** (`$D18C`);
- на **странице статуса** (`$F05A`): если **бит 6** выставлен — печатается
  строка `CLOAKING DEVICE`.

**Вывод: невидимость не покупается — её получают как награду за миссию.**
Это ровно то, о чём вы говорите. Механика награды-предмета подтверждена кодом.

**2. `ECM JAMMER` — тоже НЕ покупается.**
Строка `JAMMER` берётся из токена `$CE`. На странице статуса (`$F015`–`$F01C`):

> Если **бит 7** mission_flags установлен — печатается строка **` JAMMER`**
> **вместо** строки E.C.M.

То есть глушитель тоже привязан к миссии (бит 7 = миссия принята/активна),
а не к магазину.

### 12.6. Итог по достоверности

| Утверждение | Статус |
|---|---|
| Миссия «Сверхновая» существует | ✅ подтверждено кодом |
| Миссии в Spectrum есть, их набор ≠ BBC | ✅ подтверждено |
| Таргоидская ветка миссий есть | ✅ подтверждено (токены + корабли) |
| Невидимость — награда за миссию, не покупка | ✅ подтверждено кодом |
| Глушитель E.C.M. — привязан к миссии | ✅ подтверждено кодом |
| Constrictor есть в Spectrum | ❌ **опровергнуто** (0 совпадений) |
| «Захват корабля Таргоидов», «тяжёлый крейсер» | ⚠️ не проверено |

### 12.7. Что это даёт концепции

Сложилась цельная картина, и она лучше, чем «одна миссия»:

1. **Миссии — не текстовые вставки, а флаги с последствиями.** Бит 7
   одновременно отключает боевой ИИ, меняет страницу статуса и держит
   специальный груз. Это готовая, компактная архитектура — 4 бита на всё.
2. **Награда предметом работает.** Невидимость и глушитель — не товар,
   а следствие флага. Для idle это идеально: предмет-награда не ломает
   экономику, потому что его нельзя купить.
3. **Миссия «Сверхновая» хорошо ложится на наши решения:** FUEL LEAK
   сжигает топливо → стыковка-мини-игра даёт напряжение → прыжок из дока
   (баг, раздел 11.2) становится буквальным выходом.
4. **Отступление, которое стоит обсудить:** Constrictor и прочие
   BBC-миссии мы можем взять как «свои», даже если их нет в Spectrum —
   пользователь играл в Spectrum, но концепция не обязана копировать
   ровно один порт. Это не противоречит принципу «по исходникам», если
   явно помечать источник каждой миссии.

## 13. МИССИИ ПО ВЕРСИЯМ: 48K vs 128K, и «крейсер»

Раздел 12 был записан с ошибкой в 12.3 — исправлено. Здесь полная картина.

### 13.1. Ключевое открытие: две разные версии Spectrum

`reference/elite-zx-skoolkit` — дизассемблер **48K**-версии:
снапшот `elite.z80` = 43 794 байта, все адреса ≤ `$DFFF`, никаких банков памяти.

**Миссии Constrictor и Thargoid Documents в 48K-версии отсутствуют.** Они
появились только в **128K**-версии (`Elite 128k`, Firebird/Torus 1985 и её
переиздания 1993 года).

Подтверждение из обсуждений (коды доступа к миссиям в 128K): миссия «Cloaked Asp»
включается после **128 прыжков**, миссия «Thargoid attack» — после **254 прыжков**,
и обе — только вне первой галактики.

**Это третий раз, когда урок «нет в одном источнике ≠ нет в игре» подтвердился.**
Первый раз — BBC vs Spectrum (раздел 9), второй — библиотека Моксона,
третий — 48K vs 128K. Правило усиливается: **любой вопрос об оригинале требует
указания не только компьютера, но и конкретной версии.**

### 13.2. Ответ про «тяжёлый крейсер Таргоидов» — его нет

Прочесал Spectrum-дизассемблер по словам `cruiser`, `CRUISER`, `warship`,
`battle`, `giant`, `leviathan` — **всё по нулям**.

Что реально есть в коде: `mothership` (5 упоминаний) — это **не отдельный
корабль**, а роль: «Thargoid mothership» = Thargoid, который несёт и
выпускает **Thargon'ов** (дроны). Один и тот же корабль, две роли.

**Вывод: «тяжёлый крейсер Таргоидов» — это, скорее всего, пересказ
форумных легенд о других портах (Atari ST, Amiga, PC Elite Plus).**
В Spectrum его нет ни в 48K, ни (по всем признакам) в 128K.

### 13.3. Полный набор миссий по версиям

| Миссия | BBC | Spectrum 48K | Spectrum 128K | MSX / Atari ST |
|---|---|---|---|---|
| Constrictor | ✅ (256 убийств, гал. 1–2) | ❌ | ✅ (128 прыжков) | ✅ |
| Thargoid Documents | ✅ | ❌ | ✅ | ✅ |
| Supernova | ❌ | ✅ | ✅ | ✅ |
| Thargoid Invasion | ❌ | ❌ | ✅ (254 прыжка) | ✅ |
| Cloaking Device | ❌ | ⚠️ (см. 12.5) | ✅ | ✅ |
| Trumbles (Трибблы) | ❌ | ❌ | ❌ | Только C64/PC+/Apple |

Источник: скриншот фактов из `alt.fan.elite` FAQ и треды Frontier Forums
(128K «Elite 3», 1993) + собственный поиск по коду.

### 13.4. Что «сотрудники» говорят про награды — и что подтвердил код

Из нескольких независимых источников совпадает:

- **Supernova** → gem-stones (в Spectrum — **100 г**, пользователь помнит
  и подтверждение есть);
- **Constrictor** → деньги (10 000 CR в MSX/Atari ST; в разных версиях
  по-разному, до 10 000);
- **Thargoid Documents** → **Naval Energy Unit** (энергетический блок,
  заряжает энергию вдвое быстрее) **или** 5 000 CR в зависимости от версии;
- **Thargoid Invasion** → **ECM Jammer** + титул **«Archangel»**;
- **Cloaking Device** → сам прибор; получают **подбором канистры** после
  уничтожения особого корабля (Cougar/Constrictor — зависит от версии).

Наш код подтвердил механику выдачи (12.5): невидимость и глушитель
**не продаются**, а выдаются по mission-флагу. Это согласуется.

### 13.5. Важное открытие для раздела 11.3 (тупик)

Нашёл **встроенный выход из тупика в оригинале**, и он родом из миссии
Supernova.

По описаниям: когда заканчивается топливо, игра предлагает **черпать
топливо из звезды** (fuel scoop / топливозаборник). В самом Spectrum-коде:

- `Token $00`: **`FUEL SCOOPS ON`** — рекурсивный токен, выводится
  на приборную панель;
- `scoop` — 26 упоминаний в коде, `scoop_commodity` — сбор груза;
- `fuel scoop` — 7 упоминаний.

**Что это значит для нас.** Тупик «топливо 0 + деньги 0» в оригинале не был
тупиком: **звезда — это бесплатный источник топлива**. У нас в игре звезды
как объекта нет вообще.

**Кандидат на решение (обсуждается):** добавить «черпание из звезды» как
бесплатный, медленный и **всегда доступный** способ заправки. Тогда:

- тупик невозможен по построению;
- механика взята из оригинала, а не выдумана;
- она не ломает экономику — по времени она должна быть невыгодна
  по сравнению с купленным топливом;
- в idle это идеально: пассивный доход, который никогда не равен нулю,
  но и не даёт разбогатеть.

**Это, возможно, лучшее решение вопроса 11.3** — не костыль, а возврат
к утраченной механике.

### 13.6. Про смешивание версий — решение пользователя

Пользователь разрешил **смешивать миссии из разных версий**.
Значит концепция не обязана копировать один порт.

**Предлагаемый принцип (на утверждение):**

> Каждая миссия переносится из **самой полной версии**, в которой она есть,
> с явной пометкой источника в документации. Набор — не «как в Spectrum»,
> а «всё лучшее, что было в Elite», с приоритетом того, что игрок помнит.

Приоритет по «памяти игрока»: Supernova (помнит) > Constrictor, Thargoid
Invasions, Cloaking Device.

### 13.7. РЕШЕНИЯ ПОЛЬЗОВАТЕЛЯ (2026-11-13)

Три вопроса закрыты.

**1. Звезда — как объект. И не только звезда.**

> «Звезда — как объект (желательно все объекты из оригинала — как объект)».

Значит принимается **объектная модель мира**: планеты, звёзды, станции,
корабли, контейнеры, астероиды — всё существует как отдельная сущность
с собственными свойствами и координатами, а не как абстрактный параметр
системы.

Это решение **согласуется с уже принятым** (раздел 11.4, кабина как окно):
если мир объектный, кабине есть что показывать. И оно делает «черпание
из звезды» (13.5) естественной операцией над объектом, а не отдельной
кнопкой.

**Следствие для реализации:** нужен объектный слой мира
(`World` → `System` → `Entity[]`), где звезда — такая же сущность, как
станция. Сейчас в `state.ts` этого нет: система — это набор полей.

**2. Миссии: на старте — ноль, в релизе — обязательно.**

> «Можно совсем без миссий на старте, но они обязательно нужны в релизе».

Значит миссии **не входят в MVP**, но входят в **обязательный объём релиза**.
Это снимает вопрос — не «делать ли», а «когда».

Порядок работ в связи с этим сдвигается: сначала ядро (мир, объекты,
полёт, стыковка, экономика), миссии — после того, как ядро устойчиво.

**3. PR #3 — влит.**

Слияние в `main` выполнено, ветка синхронизирована, конфликт был только
в этом файле и разрешён. Тесты: **166/167**, `tsc` чистый.

### 13.8. Уточнение приоритета

Раз миссии уходят за MVP, а объектная модель — в MVP, порядок такой:

1. **Объектная модель мира** (звезда, планета, станция, корабль) — новое,
   крупное, но оно фундамент для всего остального;
2. **Черпание топлива из звезды** — как следствие объектной модели
   и как решение тупика 11.3;
3. полёт / кабина / стыковка;
4. миссии (в релиз, не в MVP).

  (Вопрос из миссии, отложен вместе с миссиями.)
- Состав миссий в релизе: все пять или подмножество.

## 14. ОБЪЕКТНАЯ МОДЕЛЬ: решения и архитектура

### 14.1. Как устроен оригинал (подтверждено кодом ZX Spectrum)

Проверено по `reference/elite-zx-skoolkit`:

- **Восемь слотов кораблей** — массив с `$6048`, по `$27` (39) байт на запись.
  Больше восьми объектов одновременно **физически не существует**.
  Живого мира в Elite никогда не было.
- **Слот 0 — не игрок.** Игрок сидит в начале координат. Слот 0 держит объект,
  на который смотрит **компас** — планету или станцию.
- **Отслеживается ровно два объекта** (`$7107`, `$7110`, по 9 байт позиции
  sign-magnitude). Засеиваются из сида системы при прибытии и вращаются
  с видом каждый кадр.
- **Пороги дистанции:** `$4000` и `$2000`. Ближе `$2000` — «объект близко»
  (`$711E`), что и включает черпание топлива (если стоят скопы).

**Вывод:** упрощённая модель пользователя — не отступление от оригинала.
Это сам оригинал. Защищать отход не требуется.

### 14.2. Топливные скопы — покупать, как в оригинале

Решение пользователя: скопы остаются **покупаемым оборудованием**.

**Проблема, которую это создаёт (исправление ошибки агента):** в предыдущем
обсуждении было сказано, что звезда решает тупик 11.3. Это **неверно**.
Черпание требует *двух* условий: объект ближе `$2000` **и** установленные
скопы (`$D088`). При 0 кредитов и без скопов тупик возвращается.

### 14.3. Идея пользователя: кредит под проценты (ОТЛОЖЕНО)

> «Чтобы не застрять — кредит под проценты, который можно не отдавать,
> улетев в другую галактику».

**Механика:** игрок может взять ссуду. Начисляются проценты. Долг можно
«списать», совершив галактический прыжок — то есть сбежав из галактики.

**Почему это хорошо:**
- закрывает тупик 11.3 без костылей — деньгами, а не запретами;
- вписано в лор: галактический двигатель уже есть (5 000 CR, одноразовый),
  и он становится **билетом из долговой ямы**;
- создаёт настоящее решение: долг 8 000 CR и двигатель за 5 000 → прыжок
  выгоден; долг 2 000 → проще заплатить;
- это отступление от оригинала, но отступление **по мотивам**: в оригинале
  долгов нет вообще, зато есть одноразовый билет в другую галактику.

**Открытые вопросы (вернуться позже):**
- как не допустить цикл «взял кредит → прыгнул → взял снова»? (лимит в одну
  галактику? репутация? размер кредита зависит от того, сколько раз бежал?)
- проценты — какие? фиксированные или растущие?
- кредит выдаётся только в доке?
- что происходит с долгом при смерти?

**Статус:** идея принята к рассмотрению, реализация отложена.

### 14.4. Сколько объектов в системе — решение агента

Оригинал ограничен восемью слотами. Предлагаю **сохранить это ограничение** —
оно не мешает, но красиво и честно:

| Тип | Сколько | Роль |
|---|---|---|
| Звезда | 1 | черпание топлива, миссия «Сверхновая» |
| Станция | 1 | стыковка, торговля |
| Планета | 1 | визуальный якорь, данные, миссии |
| Корабли (пираты/торговцы) | до 4 | бой |
| Контейнеры | до 4 | сбор груза |
| Астероиды | до 4 | добывающий лазер |

**Всего не больше 8 одновременно**, как в оригинале. Три постоянных + до пяти
динамических, вытесняющих друг друга по приоритету.

Почему так: 8 — не наше изобретение, а проверенный предел. Меньше 8 не нужно:
станция, звезда и планета нужны всегда, а на встречи остаётся пять слотов.
Больше 8 — уже не Elite, и UI кабины станет нечитаемым.

### 14.5. Кабина: компас с автоматическим разворотом

Схема пользователя (обсуждается и принята как направление):

1. после прыжка или на старте — видим вращающуюся станцию;
2. кнопка «развернуться к солнцу / другому объекту на радаре»;
3. дальнейшее взаимодействие — отдельными кнопками/мини-играми.

**Сопоставление с оригиналом:**

| Схема пользователя | Оригинал |
|---|---|
| вращающаяся станция впереди | слот 0, объект компаса |
| «развернуться к объекту» | компас показывает направление; крутить надо вручную |
| взаимодействие кнопкой | `$711E` «объект близко» → действие |

**Отход от оригинала минимален и обоснован:** убираем ручное кручение
(главный источник утомления), заменяем компасом с автоповоротом.

### 14.6. «Давление» — что имелось в виду

Это не давление на игрока, а **причина нажимать кнопки**.

Без давления схема «увидел → развернулся → взаимодействовал» превращается
в меню: три клика, ноль решений, ноль риска. Играть нечего — как бы красиво
это ни выглядело.

Давление = **что стоит на кону** и **чем грозит промах**.

Три вида давления, и они по-разному сочетаются с idle:

1. **Время** (реальный таймер, не успел — провал). Плохо для idle:
   требует присутствия, наказывает за отсутствие.
2. **Ресурс** (промах отнимает топливо/груз/прочность). Терпимо: последствия
   есть, но игра идёт дальше.
3. **Качество** (идеально / хорошо / плохо — награда за внимание, но **без
   наказания** за отсутствие). Лучше всего для idle.

**Предложение:** использовать (3) как основу, (2) — как верхний уровень риска.
Принцип уже зафиксирован в 11.4: **кабина даёт преимущество, а не требует
присутствия.** Хорошо сыграл — получил больше; не играл — не потерял ничего,
но и не выиграл.

**Пример на стыковке:**
- нет давления: «нажмите — пристыковались» (это кнопка, не игра);
- давление качеством: станция вращается, есть окно стыковки. В окно — «чистая
  стыковка» (+бонус к цене продажи или опыт). Мимо — обычная стыковка,
  без штрафа;
- давление ресурсом: мимо окна — повреждение части груза.

### 14.7. Что остаётся решить

- какой вид давления выбрать для каждой мини-игры (стыковка, черпание, сбор);
- можно ли черпать топливо **без** скопов (сейчас по оригиналу — нет,
  что и возвращает тупик);
- детали кредита (14.3).

## 15. СТЫКОВКА: мини-игра со ставкой

### 15.1. Решение: без скопов нельзя

Пользователь: **«без скопов нельзя»**. Принято, строго по оригиналу.

Тупик 11.3 (топливо 0 + деньги 0 + нет скопов) закрывается **только кредитом**
(14.3, отложен). Это осознанное решение: дыра признана, костылём не латается,
закрывать её будем деньгами, когда дойдёт очередь.

### 15.2. Подтверждение из кода: стыковка в оригинале — тоже «ставка»

Пользователь предложил мини-игру со ставкой. Проверка кода показывает, что
это **не отступление, а прочтение оригинала**.

`$9A59` (по `$7471`, каждый кадр во время стыковочной последовательности):

> Пока флаг `$7104` (стыковка идёт) установлен, рутина подтягивает
> приборные полосы 1 и 2 к целевым значениям по таймерам `$9CA3`/`$9CA4`
> через `$9AA7`. **Большой шаг там может вызвать бросок на повреждения
> `$D1E9`, поэтому грубый подход к стыковке может стоить груза или
> оборудования.**

То есть в оригинале:
- **плавный подход → ничего не теряешь**;
- **резкий → бросок на повреждения → теряешь груз или оборудование**.

**Это буквально «ставка»: аккуратность обменивается на риск потери.**
Механика пользователя воспроизводит оригинал точнее, чем «нажал кнопку».

### 15.3. Три оси мини-игры (схема пользователя)

> «Совместить оси вращения станции и корабля, затем совместить само вращение,
> так же важна скорость сближения».

Три параметра, каждый — отдельная шкала:

| Ось | Что значит | В оригинале |
|---|---|---|
| **Ориентация** (оси) | куда «смотрит» корабль относительно стыковочного слота | игрок должен встать в створ |
| **Вращение** (roll) | вращение корабля совпадает с вращением станции | классическая сложность Elite |
| **Скорость сближения** | слишком быстро — разбился, слишком медленно — не успел | `$82D7`: полосы «далеко/средне/близко» |

Оригинал отслеживает эти величины: `$82D7` ведёт полосы подхода через
значения `$63` (далеко) → `$02` (средне) → `$06` (близко), а `$711F` —
флаг «в пределах стыковочной дистанции».

### 15.4. Как обыграть: три кольца вместо трёх кнопок

Предложение агента (обсуждается).

**Визуально:** в кабине — станция (вращается) и **три кольца-индикатора**:

1. **Кольцо ориентации** — расхождение осей. Чем ближе к нулю, тем плотнее
   сходится кольцо в точку.
2. **Кольцо вращения** — надо попасть в фазу вращения станции. Метка
   бежит по кругу; поймал в нужной точке — совпало.
3. **Полоса скорости** — не шкала «больше/меньше», а **зелёная зона**.
   Внутри — нормально, снаружи — риск.

**Управление — две кнопки**, не три:
- **«Сближение»** — приближает;
- **«Выравнивание»** — подтягивает кольца.

**Почему две, а не три:** три параметра и три кнопки — это уже симулятор.
Две кнопки + зона качества сохраняют «нажал и смотри», но дают навык.

**Ставка (это главное):** перед сближением игрок **выбирает темп**:
- **осторожно** — медленно, почти без риска, малая награда;
- **обычно** — середина;
- **рискованно** — быстро, большой бонус, реальный шанс потерять груз.

Это и есть «ставка»: игрок сам решает, на что играет. Промах при «рискованно»
бьёт по грузу (как `$D1E9` в оригинале), при «осторожно» — не бьёт вовсе.

### 15.5. Награда за качество

Попадание во все три кольца = **чистая стыковка**. Что она даёт:

- лучшую цену на продажу (сговорчивый торговец);
- отсутствие износа;
- бонус к репутации/опыту.

Промах = обычная стыковка без бонуса. **Никогда не блокирует игру** —
соблюдает принцип 11.4 («кабина даёт преимущество, а не требует присутствия»).

### 15.6. Почему это работает для idle

- **Не играешь вообще** — стыковка авто, без бонуса. Игра идёт.
- **Играешь на «осторожно»** — небольшой стабильный бонус.
- **Играешь на «рискованно»** — большой бонус, но можно потерять груз.

Три уровня вовлечённости, все жизнеспособны. Игрок сам выбирает свою глубину —
это и есть то, чего не хватало.

### 15.7. Побочная находка: оружие нельзя продать с прибылью

Не связано с кабиной, но найдено при проверке и стоит запомнить.

`$B7AC`: каждый кадр, пока игрок в пределах стыковочной дистанции,
обнуляются первые два байта записи 10 (`$7043`/`$7044`) — базис и
экономический градиент **FIREARMS** (токен `$3A`) в таблице цен `$701B`.

`$E148` перестраивает таблицу только при гиперпрыжке, поэтому к моменту
стыковки база Firearms уже нулевая, а `$E6FA` принудительно ставит
фиксированную цену `$02C0`.

**Итог: цена Firearms одинакова на покупку и на продажу в любой станции,
куда игрок долетает. Заработать на оружии нельзя.** Это защита от
эксплойта, встроенная в оригинал.

## 16. УПРАВЛЕНИЕ СТЫКОВКОЙ: ползунок + два импульса вращения

### 16.1. Предложение пользователя

> «Ползунок скорости сближения и две кнопки — вращение по и против часовой
> стрелки. Наподобие: кнопка вращения даёт импульс вращения».

То есть **не удержание**, а **толчок**: нажал — корабль получил
угловую скорость, дальше крутится сам, пока не скомпенсируешь.

### 16.2. Это оригинал, а не отступление

Проверка кода ZX Spectrum (`$6048`+`$1D`, документация байта записи корабля):

> `$1D` — **Roll counter** (BBC байт #29): **бит 7 установлен — вращаться
> непрерывно** (`$C0` по умолчанию). Если сброшен — **биты 0–3 отсчитывают
> вниз оставшиеся кадры вращения**, а **бит 6 — направление** (`$9FC0`).

Реализация `$9FC0`:

```
LD A,(IX+$1D)     ; взять счётчик
BIT 7,A           ; бит 7 = режим "непрерывно"?
JR NZ,$9FD3       ;   да → сразу на выдачу
AND $0F           ; младшие 4 бита = сколько кадров осталось
JR Z,$9FDD        ;   ноль → скорость 0, вращение кончилось
DEC A             ;   иначе уменьшить на 1 кадр
LD (IX+$1D),A     ;   и сохранить
...
$9FD3: A = $0C
BIT 6,(IX+$1D)    ; бит 6 = направление
JR Z,$9FDD
ADD A,$80         ;   положительный знак для другого направления
```

**Что это даёт:**
- **биты 0–3 (значение 0–15) — это ровно «длительность импульса»**;
- **бит 6 — направление** (по / против часовой);
- **бит 7 — режим «крутится всегда»** (по умолчанию `$C0` = 1100 0000:
  непрерывно, против часовой).

**Вывод: в оригинале кнопка вращения и есть импульс.** Нажал — записалось
число кадров, корабль крутится это время и останавливается. Мгновенной
скорости у корабля нет вообще.

### 16.3. Что это значит для модели

Наша модель получается **честнее**, чем «держать кнопку»:

```
импульс: ω += DIR * K          // нажал — прибавилось
кадр:    ω *= (1 - затухание)  // крутится и постепенно замедляется
```

Игрок нажимает, смотрит, как кольцо расхождения уходит, и **нажимает
навстречу**, чтобы остановить. Это тот самый навык «погасить вращение»,
который в Elite считался главной сложностью стыковки.

**Важное следствие:** стик «нажал вправо — крутится вправо, нажал влево —
крутится влево» (как в аркадах) **не подходит**. Он ломает модель импульса:
в оригинале вращение имеет **инерцию**, и бороться с инерцией — суть игры.

### 16.4. Комплект управления

| Элемент | Тип | Что делает |
|---|---|---|
| Ползунок скорости | непрерывный | задаёт скорость сближения |
| Кнопка «по часовой» | импульс | `ω += +K` |
| Кнопка «против часовой» | импульс | `ω += −K` |

Два импульса работают как **разгон и торможение** одного и того же вращения.
Это и есть суть: не «куда повернуть», а **сколько и когда**.

### 16.5. Что даёт по сравнению с тремя кольцами (15.4)

Модель пользователя **проще и лучше** предыдущей:

- **нет третьего кольца** — скорость сближения управляется ползунком,
  а не отдельной шкалой-заданием;
- **два импульса вместо двух кнопок «Сближение/Выравнивание»** — и они
  напрямую соответствуют оригиналу;
- **меньше сущностей**, больше навыка: одно большое кольцо ориентации
  + индикатор скорости.

**Ставка (15.4) сохраняется:** перед стыковкой игрок выбирает темп —
осторожно / обычно / рискованно. Ползунок задаёт скорость **внутри**
выбранного темпа, а не заменяет его.

### 16.6. Как выглядит в кабине

```
┌─────────────────────────────────────────┐
│                                         │
│           ╱‾‾‾‾‾‾‾╲                       │  ← станция вращается
│          │  КОЛЬЦО  │                      │  ← кольцо ориентации
│          │    ◎     │                      │     (сходится в точку)
│           ╲_______╱                       │
│                                         │
│  [◀]   [▶]        СКОРОСТЬ              │
│  против  по        ├──●────────┤         │
│  часовой часовой    медленно  быстро    │
│                                         │
│         СТАВКА: ○осторожно ●обычно ○риск│
└─────────────────────────────────────────┘
```

- кольцо расхождения **само сходится**, когда вращение скомпенсировано;
- рядом с кольцом — **стрелка текущего ω**, чтобы было видно, куда крутит;
- ползунок показывает скорость; **зелёная зона** — безопасная;
- ставка выбирается **до** начала и меняет цену ошибки.

### 16.7. Почему это хорошо для idle

Нажатие импульса — **редкое и осмысленное действие**, а не непрерывное
удержание. Игрок может:
- зайти, дать два импульса, уйти — стыковка идёт;
- подождать и подстроить — получить чистую стыковку.

Не требует присутствия, но вознаграждает внимание. Принцип 11.4 соблюдён.

### 16.8. ИСПРАВЛЕНИЕ: затухание — опция, а не поведение по умолчанию

Агент ошибочно утверждал, что в оригинале вращение «само затухает».
Пользователь возразил: «уверен, что было затухание, я такого не помню».
**Пользователь прав.**

Проверка `$FE01` (`update_control_rates`, используется прерыванием):

> Читает биты управления за кадр (`$FC09`) и **байт опций управления
> `$FC0E`**, затем трижды прогоняет логику «подтолкнуть или уменьшить
> скорость с ограничением» на трёх счётчиках: `roll_rate_accum` (вращение,
> клавиши N/M), `dive_climb_rate_accum` (пике/кабрирование, X/S) и
> `speed_rate_accum` (**скорость, SPACE / SYMBOL SHIFT**).
>
> **Для вращения с отпущенными клавишами:** затухание скорости к нулю
> фиксированным шагом — **только если установлен бит 3 байта `$FC0E`,
> опция «keyboard damping»; иначе скорость остаётся без изменений**.

Чтение `$730A` (`toggle_damping_key_d`, клавиша **D**):

> Переключает бит 3 `$FC0E` — документированный в игре
> **«переключатель клавиатурного демпфирования»**, который
> **отключает/включает автоматическое затухание** вращения/пике/скорости
> при управлении с клавиатуры.

**Вывод: затухание — отключаемая опция, а не закон физики.**
По умолчанию в оригинале корабль **сохраняет угловую скорость** после
отпускания клавиши. Именно поэтому игроки Elite помнят управление как
«инерционное», а не «вязкое».

**Что берём в мини-игру:** затухание = 0 (или очень малое).
Игрок гасит вращение **сам**, нажимая навстречу. Это и есть навык.

### 16.9. Скорость тоже импульсами — предложение пользователя

> «Возможно ли сделать скорость тоже импульсами, вперёд и назад?
> Тогда без ползунка».

**Подтверждение кодом:** в `$FE01` скорость — **третий точно такой же
счётчик** (`speed_rate_accum`), с тем же «подтолкнуть/уменьшить»
и клавишами SPACE (увеличить) / SYMBOL SHIFT (уменьшить).

То есть **в оригинале скорость управляется точно так же, как вращение** —
импульсами, а не ползунком. Ползунок был **нашим изобретением**, а не
оригиналом. Предложение пользователя возвращает верность источнику
и одновременно упрощает интерфейс.

**Итог: четыре импульсные кнопки, ноль ползунков.**

| Кнопка | Действие | Оригинал |
|---|---|---|
| ◀ | вращение против часовой | N |
| ▶ | вращение по часовой | M |
| ▲ | увеличить скорость | SPACE |
| ▼ | уменьшить скорость | SYMBOL SHIFT |

### 16.10. Открытые вопросы (обновлено)

- затухание: берём 0 (нет затухания) — подтверждено кодом как поведение
  по умолчанию;
- сколько «единиц» даёт одно нажатие и как это отображается;
- плавность ползунка: он задаёт **целевую** скорость или **текущую**
  (в оригинале скорость набирается через ускорение `$1C`).

## 17. ПРОТОТИП МИНИ-ИГРЫ СТЫКОВКИ (HTML)

### 17.1. Зачем

Обсуждать механику словами дальше бесполезно — нужны **ощущения**.
Сделан работающий прототип, чтобы проверить: интересно ли, понятно ли,

**Файл:** `prototype/docking.html` — открывается в браузере, зависимостей нет.
**Запуск:** `python3 -m http.server 8080 --directory prototype`
→ `http://localhost:8080/docking.html`

### 17.2. Что в нём реализовано

**Управление — четыре импульса, ноль ползунков** (по решению 16.9):

| Кнопка | Действие | Клавиши |
|---|---|---|
| ◀ | вращение против часовой | ← или N |
| ▶ | вращение по часовой | → или M |
| ▲ | увеличить скорость | ↑ или SPACE |
| ▼ | уменьшить скорость | ↓ |

Удержание кнопки даёт повтор импульсов — но **каждое нажатие само
по себе импульс**, как в оригинале.

**Модель:**
- затухания вращения **нет** (подтверждено кодом, 16.8);
- скорость и вращение — независимые счётчики с ограничением сверху;
- станция вращается сама — к её вращению надо подстроиться;
- стыковка происходит при сближении: проверяются створ, совпадение
  вращения и попадание в коридор скорости.

**Три ставки (15.4) реально влияют:**
- **осторожно** — промах ничего не ломает;
- **обычно** — промах отнимает 30% груза;
- **рискованно** — промах отнимает 85% груза, а станция вращается быстрее.

**Чистая стыковка** = створ совпал + вращение совпало + скорость в коридоре.

### 17.3. Что проверяется прототипом

1. **Читаемость**: понятно ли с первого взгляда, чего не хватает для стыковки?
2. **Ощущение импульса**: не раздражает ли, что кнопка не «держит», а «толкает»?
3. **Сложность**: реально ли попасть в створ, или это мучение?
4. **Ставка**: ощущается ли разница между «осторожно» и «рискованно»?
5. **Idle-совместимость**: можно ли отойти и вернуться?

### 17.4. Известные ограничения прототипа

- визуал схематичный (не финальный), станция — ромб, не настоящая модель
  из Elite (`ship_coriolis`);
- нет звука;
- нет связи с игрой — это изолированная сцена;
- параметры (`ROLL_IMPULSE`, `SAFE_SPEED` и т.д.) подобраны на глаз,
  а не выведены из оригинала.

## 18. ПРОТОТИП: исправление вращения станции + задний ход

### 18.1. Баг: станция не вращалась

**Симптом (пользователь):** «там не было вращения».

**Причина:** `stationRoll` инициализировался нулём в объекте состояния
и **переустанавливался только внутри `reset()`**, которая при загрузке
не вызывалась. То есть до первого нажатия R станция стояла.

**Исправление:** вынесено в отдельную функцию `seedStation()`:

```js
function seedStation() {
  const base = 0.22 + Math.random() * 0.18;        // 0.22..0.40 рад/сек
  const speed = base * (0.7 + bet.spawnDrift * 0.8);
  S.stationRoll = (Math.random() < 0.5 ? -1 : 1) * speed;
  S.stationAngle = Math.random() * Math.PI * 2;
}
```

Вызывается и при загрузке, и в `reset()`. Направление вращения случайное,
скорость зависит от ставки (на «рискованно» станция крутится быстрее).

Проверено: 1000/1000 случаев станция вращается.

### 18.2. Задний ход

**Запрос пользователя:** «нужно реализовать задний ход».

**Реализация:**
- `SPEED_MIN` изменён с `0.0` на `−0.5` — отрицательная скорость = задний ход;
- расстояние **растёт** при заднем ходе (`dist -= speed * dt`), ограничено
  `MAX_BACK = 160` — уехать бесконечно нельзя, это манёвр, а не побег;
- шкала скорости переделана в двустороннюю: ноль по центру, слева задний ход,
  справа передний;
- задний ход окрашивается в голубой (CYAN) — отличается от «слишком медленно»;
- HUD показывает «◀ назад» / «вперёд».

**Важно для стыковки:** при заднем ходе `speedPenalty()` возвращает `1` —
**стыковка невозможна**. Задний ход нужен, чтобы отойти и перезайти на цель,
а не чтобы пристыковаться.

**Оговорка о верности оригиналу:** в Elite заднего хода в этом смысле нет —
скорость там от 0 до максимума, а «назад» это разворот корабля на 180°.
Наша реализация — **отступление ради удобства** мини-игры: разворачивать
корабль в 2D-схеме бессмысленно. Отступление маленькое и обоснованное.

### 18.3. Проверка

Синтаксис JS — чистый (`new Function`). Логика проверена в Node:

| Проверка | Результат |
|---|---|
| станция вращается при загрузке | 1000/1000 |
| 8 нажатий ▼ → −0.50 (предел) | ✅ |
| задний ход: 100 → 103 (растёт) | ✅ |
| 15 нажатий ▲ → 1.00 (предел) | ✅ |
| передний ход: 100 → 94 (падает) | ✅ |

## 19. РАЗБОР: как в оригинале отображается скорость и что реально бьёт корабль

Пользователь задал два вопроса, оба точные.

### 19.1. Скорость в оригинале — НЕ в цифрах

Две разные вещи, которые легко спутать:

**1. Газ — это полоска.**
`$713C` (`seed_demo_ship_rates`) пишет копию скорости для приборной панели:

> ...и байт скорости, масштабированный как `5 * (байт + 1)`,
> в `$70F4` (**бар 7**). `$84D9` рисует все три каждый кадр.

**Бар 7 — длина полоски, не число.** То есть «на сколько выжат газ» —
это **шкала**, как и всё остальное на панели.

**2. Цифра скорости на экране есть, но это другое.** В Elite на приборной
панели показывается **скорость** числом — но это *не газ*, а
**фактическая скорость** корабля (после инерции и т.п.). Газ — полоска.

**Важное следствие для нашей мини-игры.** У нас нет инерции, поэтому
газ и скорость — одно и то же. Значит:
- либо показываем **полоску** (как оригинал),
- либо показываем **число** (как оригинал, но у нас это же и газ).

**Полоска вернее**: она воспроизводит оригинал и не создаёт ложного
ощущения точности. Цифры можно добавить мелким шрифтом для отладки.

### 19.2. Угол захода — влияет ли он на повреждения?

Пользователь помнит, что «угол захода в док влиял на повреждения».
**Пользователь прав, но механика работает иначе, чем кажется.**

В оригинале НЕТ проверки «под каким углом вошёл в створ». Есть другое:

`$9A59` (стыковочная последовательность): пока идёт стыковка, значения
приборных полос подтягиваются к цели шагом по таймерам `$9CA3`/`$9CA4`
через `$9AA7`. И вот ключевое:

`$9AA7` (`step_or_refill_bar_gauge`):

> Если A не ноль и используется как длина полосы: **если шаг большой
> (A ≥ `$46`), сначала вызывается `$D0F3` (`$D1E9` — случайный бросок
> на повреждение груза/оборудования)**; затем A вычитается из до 4 байт
> по адресу (HL).

А `$D1E9` (`maybe_damage_on_hit`) — это **не про угол**:

```
LD A,($7105)   ; случайное 0-63 из сида
RRCA / RRCA
AND $3F
JP Z,$DE97     ; 0 → отдельная ветка
CP $11
RET NC         ; 11+ (большая часть диапазона) → НИЧЕГО
DEC A
CP $06
JR NC,$D21F    ; 7-16 → уничтожить единицу груза
               ; 1-6  → выбить единицу ОБОРУДОВАНИЯ
```

**Вывод: повреждение определяется случайным броском, а не углом.**
Угол влияет **косвенно**: плохой заход → большой шаг → срабатывает бросок.
Но бросок может ничего не сделать (значения 17–63 = 46 из 64 случаев =
**72% «ничего не случилось»**).

То есть в оригинале: **плохой заход = лотерея, а не гарантированный урон.**

### 19.3. Следствие: пользователь прав, ставки не нужны

Ставка (15.4) была придумана агентом, чтобы дать игроку выбор «на что играть».
Но если риск **уже** пропорционален качеству захода, выбор избыточен:

| Было (со ставкой) | Стало (без ставки) |
|---|---|
| выбор темпа до стыковки | нет выбора |
| темп меняет цену ошибки | цена ошибки = качество захода |
| два источника риска | **один источник: как зашёл** |

**Это чище и ближе к оригиналу.** В оригинале игрок не выбирает «играть
рискованно» — он просто заходит как умеет, и получает по заслугам.

**Причём в оригинале разброс жёстче, чем «награда за качество»:**
испортил заход — можешь потерять **оборудование**, а не только деньги.
Это сильнее и интереснее ставки.

### 19.4. Что меняем в прототипе

- **убрать три кнопки ставки** (`ОСТОРОЖНО / ОБЫЧНО / РИСКОВАННО`);
- **риск зависит от качества захода**: чем больше расхождение по осям,
  вращению и скорости в момент стыковки, тем выше шанс повреждения;
- **шкала скорости остаётся полоской** (как бар 7 в оригинале);
- добавить **шанс на повреждение оборудования** — как `$D1E9` (7–16 → груз,
  1–6 → оборудование).

Формула (черновая):

```
качество = 1 - (ошибка_осей + ошибка_вращения + ошибка_скорости) / 3
if качество > порог_чистой:  чистая стыковка, без риска
иначе: шанс_повреждения = (1 - качество) * масштаб
       при срабатывании: бросок, как $D1E9 — груз или оборудование
```

### 19.5. Открытые вопросы

- порог «чистой стыковки» — насколько строгий?
- должны ли повреждаться **и** груз, **и** оборудование, или одно из двух?
- как в idle показывать повреждение оборудования, которого у нас пока нет?
  (Может быть, на старте — только груз и деньги.)

### 20.2. Как «оси» устроены в оригинале — это КОМПАС, а не прицел

Пользователь спросил: не добавить ли 4 кнопки для перемещения «прицела»?
**Проверка кода показывает: в оригинале такого нет.**

`$81A9` (обновление компаса, каждый кадр полёта):

```
$825F CALL $8271   ; $81A6 = x слота 0 / расстояние  → горизонтальное смещение
$826C CALL $8271   ; A    = y слота 0 / расстояние  → вертикальное смещение
$829C LD ($81A7),A ; сохранить вертикальное
$829F LD A,(IX+$05)
$82A2 AND $80      ; бит 7 байта знака y
$82AA LD ($81A8),A ; флаг «объект ПОЗАДИ»
```

**Что это значит:**

- компас показывает **два числа**: `$81A6` (горизонталь) и `$81A7`
  (вертикаль) — это **доля от расстояния**, то есть куда смотреть;
- `$81A8` — «объект сзади». Когда он выставлен, точка на компасе
  **не показывается** — надо развернуться;
- рисует это `$8390`, точка на приборной панели.

**Это индикатор направления, а не орган управления.** Игрок не двигает
прицел — он **поворачивает корабль**, пока точка не встанет в центр.

### 20.3. Почему 4 кнопки для «осей» — плохая идея

Если добавить 4 кнопки перемещения прицела, получится:

| Что есть | Кнопок |
|---|---|
| вращение (◀ ▶) | 2 |
| скорость (▲ ▼) | 2 |
| прицел (← → ↑ ↓) | 4 |
| **итого** | **8** |

Восемь кнопок — это уже не idle-мини-игра, а симулятор. И главное:
**это не то, что делает оригинал.** В Elite игрок не двигает прицел —
он крутит корабль, и точка компаса сама встаёт в центр.

### 20.4. Что предлагается вместо

**Оси = положение точки на компасе. Управление — уже существующие 2 кнопки
вращения.**

```
        ┌───────────────┐
        │       ·       │   ← центр: соосность идеальна
        │    ●          │   ← точка: куда смотрит нос
        │               │
        └───────────────┘
              КОМПАС
```

- Точка **уходит от центра**, когда корабль не соосен створу;
- Вращение (◀ ▶) **двигает точку** — как в оригинале;
- Когда точка в центре — корабль соосен;
- Если объект **сзади** (`$81A8`) — точка не показывается, вместо неё
  индикатор «РАЗВЕРНИСЬ» (в оригинале именно так).

### 20.5. Почему это лучше

1. **верно оригиналу** — компас, а не прицел;
2. **не плодит кнопки** — остаются 4;
3. **физически осмысленно**: чтобы смотреть на станцию, надо повернуть
   корабль, а не подвинуть точку;
4. **даёт навык**: надо поймать точку в центре и одновременно совпасть
   по вращению — две задачи одним органом управления.

### 20.6. Что это меняет в прототипе

Сейчас в прототипе «оси» — это `alignmentError()` = разница углов,
и показывается кольцом. Это **функционально то же самое**, но:

- **кольцо** показывает «насколько плохо» (величину ошибки);
- **компас с точкой** показывает «куда смотреть» (направление).

Второе — вернее оригиналу и полезнее игроку: видно, **куда** доворачивать,
а не просто «плохо».

**Предлагаю заменить кольцо на компас с точкой.**

### 20.7. Открытые вопросы

- точка компаса: показывать её вообще при «объект сзади», или только
  индикатор «РАЗВЕРНИСЬ»? (в оригинале — второе);
- нужна ли **градусная** цифра рядом (для отладки), или чисто визуально;
- в 2D-прототипе «сзади» означает половину окружности — как это
  визуализировать, чтобы не путать с «далеко в стороне»?

## 23. РЕШЕНИЯ ПОЛЬЗОВАТЕЛЯ (2026-11-13, вторая серия)

### 23.1. А. Прототип — песочница, игра — в релизе

> «Песочница, игра на релизе».

**Принято.** `prototype/docking.html` остаётся изолированной страницей.
Игру (`src/`) не трогаем. Кабина в `main.ts` не появляется до релиза.

**Следствие:** всё, что делается в прототипе, — это **исследование**,
а не код игры. Ничего не переносится автоматически. Перенос — отдельное
решение и отдельная работа.

### 23.2. Б. Как повреждения устроены в оригинале

> «Как это реализовано в оригинале? Деньги не теряются».

**Пользователь прав: деньги не теряются.** Подтверждено кодом.

`$D1E9` (`maybe_damage_on_hit`) бросает 0–63 и делит на три исхода:

| Бросок | Что происходит |
|---|---|
| **0** | отдельная ветка `$DE97` (не повреждение) |
| **1–6** | выбивается **единица оборудования** (`$D085` + A + 2) |
| **7–16** | уничтожается **единица груза** |
| **17–63** | ничего (72% случаев) |

Разбор `$D21F` (`destroy_cargo_unit`) — как именно гибнет груз:

```
LD HL,$D067       ; база списка товаров
CALL $EB3E        ; HL = $D067 + A, где A = бросок−1 (7..16)
                  ; → $D06D..$D076, то есть ТОВАРЫ 2..11
LD A,(HL)
AND A
RET Z             ; если этого товара нет — НИЧЕГО не происходит
DEC (HL)          ; убрать ОДНУ единицу
LD HL,$D07C
INC (HL)          ; освободить ОДНУ тонну трюма
```

**Три важные детали:**

1. **теряется ровно одна единица** одного случайного товара;
2. **если этого товара нет — не теряется ничего** (проверка `AND A / RET Z`);
3. **деньги не трогаются вообще** — в коде нет ни одной ветки,
   уменьшающей баланс.

**Диапазон товаров 2–11** — это `$D067 + 2..11`. Товары 0 и 1 не попадают
(индексы в таблице цен смещены; `$D067` — база списка количества).
То есть **не все товары уязвимы** — часть списка исключена.

**Что берём:**
- повреждение = **потеря одной единицы случайного товара** из тех, что есть;
- **деньги не теряются никогда**;
- если трюм пуст — повреждения нет (нечем платить, и это честно).

### 23.3. В. Тупик — «сам виноват». Кредит отменён

> «Топливо 0 + деньги 0 — сам виноват, охотятся на пиратов или астероиды.
> Кредит не делаем. Или конец игры. Пока оставим так, потом ещё подумаем.
> Мне кажется такая ситуация маловероятна».

**Решения:**

- **кредит под проценты — ОТМЕНЁН** (раздел 14.3 закрыт, не реализуем);
- тупик — **осознанная позиция**, не баг: игрок сам загнал себя;
- **конец игры** рассматривается как допустимый исход;
- **пока оставляем как есть**, вернёмся позже.

**Проверка оценки «маловероятно».** Согласен с пользователем:
- пираты и астероиды дают **груз**, который можно продать → деньги всегда
  можно вернуть;
- значит «топливо 0 + деньги 0 + пустой трюм» требует, чтобы игрок
  **одновременно** истратил всё топливо, все деньги и весь груз;
- при живой торговле это редкая комбинация.

**Оговорка:** это верно **при условии, что встречи (пираты, астероиды)
реально происходят и дают добычу**. Если встреч нет — тупик становится
закономерностью. То есть **напрямую зависит от баланса спавна**.

### 23.4. Г. Ядро не трогаем

> «Ядро трогать не будем. Доработаем концепцию модельного мира».

**Принято.** Объектная модель (13.7, 14.4) остаётся **концепцией**.
`src/core/state.ts` не переписывается. Никакого `World → System → Entity[]`
в коде до отдельного решения.

**Это важно:** все идеи про объекты, звезду, черпание топлива, встречи
остаются на бумаге. Мы доводим **концепцию**, а не реализацию.

### 23.5. Итог: где мы находимся

**Что делаем:** концепция + песочница-прототип. Код игры не трогаем.
**Что отменено:** кредит, ставки, вращение как параметр стыковки.
**Что отложено:** объектная модель в коде, миссии, компас, окружности.
**Что остаётся в силе:** тупик как осознанный риск, повреждение = единица
груза, прототип = только скорость.

## 24. КОНЦЕПЦИЯ ВСТРЕЧ И БОЯ (по картине пользователя)

### 24.1. Что предложил пользователь

> «Во время перелёта, если встретили объект взаимодействия, приходит
> уведомление. Если игра в фоне — пауза на N времени, за которое надо
> принять решение (бежать, атаковать, прыгать). Если сражаешься — выпускать
> ракеты. Можно выводить объект вращающейся моделью. После боя подбирать
> выпавший груз».

Разбираю по пунктам, сверяя с оригиналом.

### 24.2. Пауза с таймером — сильное решение, но есть ловушка

**Идея:** событие → пауза N секунд → нужно успеть решить.

**Плюс:** это ровно то, чего не хватало в 14.6 («давление»).
Пауза с таймером создаёт **естественное давление временем**, но
**не наказывает за отсутствие** — если не успел, срабатывает
поведение по умолчанию.

**Ловушка:** если «не успел» = катастрофа, то idle превращается в игру,
которая требует присутствия. Это **противоречит принципу 11.4**
(«кабина даёт преимущество, а не требует присутствия»).

**Предлагаю правило:**
- **успел решить** → получил свой выбор;
- **не успел** → срабатывает **безопасное поведение по умолчанию**
  (например, «уклониться и уйти»), **без штрафа**;
- **никогда** «не успел = смерть».

Тогда таймер даёт темп, но не наказывает за то, что отошёл.

### 24.3. Что можно было сделать в бою — по оригиналу

Проверка кода показывает, что арсенал в Elite **больше, чем «ракеты»**:

| Действие | В оригинале | Наш статус |
|---|---|---|
| **Лазер** | `$B7B4`, 4 типа, перегрев `GNTMP` | ✅ уже есть в игре |
| **Ракета** | `$9BA7`, до 4 шт, 3 фазы | 🆕 нужно решение |
| **E.C.M.** | `$D085`, сбивает вражеские ракеты | 🆕 есть в экипировке |
| **Энергобомба** | `$7089`, одноразовая, взрывает всех | 🆕 есть в экипировке |
| **Побег** (escape pod) | `$B91E`, спасает жизнь | 🆕 есть в экипировке |
| **Прыжок** | заблокирован «масс-локом» (`$711E`) | 🆕 важно! |
| **Бегство** (разворот и уход) | свободный полёт | 🆕 в нашей модели |

**Ключевая находка: «прыгнуть» в бою нельзя.**
`$711E` (`tracked_object_near_flag`) — «mass locked»: пока объект рядом,
гиперпрыжок заблокирован. То есть **«прыжок» — не боевое действие**,
а **награда за успешный побег**: сначала надо отойти на достаточное
расстояние, и только потом прыгать.

Это важно: иначе «прыгнуть» становится кнопкой «я выиграл бой, не сражаясь».

### 24.4. Ракеты: три фазы, а не одна кнопка

`$9BA7` (`missile_key_sequence`) — конечный автомат на `$D047`:

- **фаза 0** — не заряжена;
- **фаза 1** — заряжена, ждёт захвата: пока цель не окажется **под прицелом**
  (`$9C97`), ничего не происходит;
- **фаза 2** — захват: цель защёлкнута (`$D0E3`), звучит бип;
- **пуск** — только из фазы 2 (бит 3 `$FC0B`).

То есть ракета **не летит в любого врага** — надо сначала захватить цель.
До 4 ракет (`$D083`, 4-сегментная шкала).

**Для нас:** если делать ракеты, нужен **захват цели** — иначе теряется
вся суть. Это ещё одна мини-механика, а не просто «нажать».

**Вопрос:** нужны ли ракеты в MVP или это слой на потом?

### 24.5. Вращающаяся модель объекта

Пользователь предложил выводить объект вращающейся моделькой.
**Оригинал делает ровно это** — корабли и станция рисуются каркасными
моделями (`ship_*`, `$A6DF`).

В прототипе станция уже вращается (ромб). Значит направление верное,
и это **не отступление**.

### 24.6. Подбор груза после боя

**Оригинал:** `scoop_commodity` (`$D183`/`$D190`) — подобранный контейнер
добавляется в трюм. Есть отдельная ветка `$FF` — «special pickup»
(ставит mission-флаг, даёт очки).

**Стыковка к нашему:** после боя на месте остаются контейнеры, их можно
подобрать. Это:
- даёт экономический смысл драться (а не только терять);
- объясняет, откуда берутся товары для торговли;
- **закрывает риск тупика (23.3)**: пираты дают груз → груз даёт деньги.

### 25.2. Авто-бой: отдельная тема, но рамку зафиксируем

Пользователь: «или безопасно уйти или авто бой (обсудим отдельно)».

**Важно понимать:** авто-бой — это **не** «игра играет за тебя».
Это поведение по умолчанию, когда игрок **не принял решение**.
Отсюда рамка:

- авто-бой **должен быть хуже** ручного боя — иначе ручной не нужен;
- но **не катастрофически хуже** — иначе отсутствие = наказание (нарушает 11.4);
- разумно: авто-бой **выигрывает чаще, чем проигрывает**, но тратит больше
  ресурсов (ракеты, энергию, время) и **не даёт качественных трофеев**.

Это предварительная рамка, детали — отдельно.

### 25.3. E.C.M. в оригинале — не «кнопка», а импульс с перезарядкой

Раз уж вопрос про арсенал открыт, собрал факты по `$B7F7`/`$B807`:

**E.C.M. — покупаемое оборудование** (`$D085`, не входит в 14 предметов
магазина… уточнение: **входит**, это позиция 4 списка `equip_ship`).

**Как работает (`$B82C` и далее):**

```
LD A,C        ; C = флаг E.C.M.
AND A
RET Z         ; нет E.C.M. — ничего
BIT 4,B       ; бит 4 латча ввода = клавиша E.C.M.
RET Z         ; не нажата — ничего
OR $80        ; выставить бит 7 — "E.C.M. стреляет"
LD ($D085),A  ; сохранить
LD A,$0A      ; счётчик импульса = 10
LD ($9C9B),A
```

**То есть:** нажал → **импульс длится 10 тиков** → в это время `$9C9B`
считает вниз, бит 7 держится, звук воет (`$7128` бит 5). Пока импульс
идёт, повторно нажать **нельзя**.

**Ключевое:** E.C.M. — это **не мгновенное действие**, а **окно
длительностью 10 тиков**. Оно сбивает вражеские ракеты в этом окне.

**Дополнительно:** `$B7F7` — если mission-флаг bit 7 выставлен И
`arrival_state = 4`, то **весь блок E.C.M. отключается** (см. 12.2:
во время миссии с беженцами E.C.M. не работает).

## 26. БОЙ: ракеты, таймер, сила противника и что такое «1»

### 26.1. Ракеты — упрощённая модель

> «Нажал, полетела, попала в цель, если не ECM».

**Принято.** Трёхфазная последовательность оригинала (`$D047`: 0→1→2)
**не воспроизводится**. Вместо неё:

1. нажал «ракета» → полетела;
2. попала в цель;
3. **если у цели есть E.C.M. — она её сбивает**.

**Что теряется:** захват цели (навык «подвести прицел») исчезает.
**Что остаётся:** E.C.M. как защита — то есть противоракетное решение
существует, но не у игрока, а у противника.

**Оговорка:** это заметное упрощение оригинала. Записано сознательно.

### 26.2. Таймер — 10–30 минут

> «10-30 минут».

**Принято.** Значение задаётся в настройках, диапазон — 10–30 минут.

**Важное наблюдение:** это **игровые минуты**, не реальные. При темпе игры
(перелёт 15 минут по умолчанию, см. `baseJumpMs`) 10–30 минут — это
**сопоставимо с целым перелётом**. То есть таймер решения почти равен
длительности пути — игрок получает событие примерно раз в перелёт,
и времени на решение у него с запасом.

**Это хорошо для idle:** решение не срочное, но и не бесконечное.
Если игра в фоне — она ждёт до N минут, потом срабатывает настройка
(безопасно уйти / авто-бой).

### 26.3. Сила противника — определяется blueprint'ом, а не «уровнем»

Пользователь: «сначала надо понять, как определить силу противника».
**В оригинале это решено элегантно — через blueprint корабля.**

Blueprint — `$17` (23) байт на тип корабля. Ключевые поля:

| Смещение | Что | Зачем |
|---|---|---|
| `$01` | Reference size | размер для отрисовки |
| `$02` | **AI laser-fire weighting** | `$FF` у Thargoid, `$00` у астероида (не стреляет никогда) |
| `$03`–`$05` | вершины / рёбра / грани | модель |
| `$06` | **Max speed** | скорость |
| `$07` | **Max energy** | «здоровье» |
| `$08` | **Bounty** (слово) | награда за уничтожение |
| `$0A` | Bit field | счётчик действий ИИ |
| `$0B` | Visibility distance | с какой дистанции видно |
| `$12` | Тип/особенности | Thargon `$04`, Thargoid `$0C` |

**Как это работает в бою:**

`$A640` — вероятность выстрела врага:

> Бросок 0–255 против байта `$02`. **Байт делится вдвое**, если у игрока
> боевой счёт (`$D062`) не нулевой (то есть игрок уже Dangerous и выше).

То есть **сильный игрок получает более слабых врагов** — уже встроенный
баланс.

**Скорость:** `$9FFD` — `bit 0` байта `$12` **удваивает** максимальную скорость.
**Энергия:** `$07` — прямое значение.

### 26.4. Что это значит для нас: «сила» = сумма параметров

Не нужен отдельный «уровень врага». Сила **выводится из blueprint'а**:

```
сила = f(max energy, laser weighting, max speed, bounty)
```

Примеры (по описаниям в коде):

| Корабль | Энергия | Лазер | Скорость | Оценка |
|---|---|---|---|---|
| Астероид (boulder) | — | `$00` (не стреляет) | — | безобиден |
| Sidewinder | низкая | низкий | средняя | лёгкий |
| Cobra Mk III (пират) | средняя | средний | средняя | средний |
| Asp Mk II | **150** | высокий | **40** | опасен |
| Thargoid | высокая | **`$FF`** | — | смертелен |

**Вывод: для интерфейса надо показывать не «уровень 5», а конкретику —
тип корабля и его повадки.** Игрок Elite узнавал врага **по силуэту**
и по поведению, а не по цифре.

### 26.5. Что такое «1» — я плохо спросил, переформулирую

Мой вопрос был: «ECM / энергобомба / побег — берём всё в релиз?»

**Проблема:** я смешал три разных предмета в один вопрос, и было непонятно,
что именно решать.

Разбиваю на три отдельных:

**1а. E.C.M.** — покупаемое оборудование. Импульс 10 тиков (`$9C9B`),
сбивает вражеские ракеты. Для нашей модели ракет (26.1) это **единственная
защита**, поэтому кажется обязательным.

**1б. Энергобомба** — `$7089`. Одноразовая, уничтожает **всех NPC** на поле,
флашит экран 24 раза. Мощно и просто. Вопрос: не слишком ли «кнопка
победить»?

**1в. Побег (escape pod)** — `$B91E`. Спасает жизнь: выбрасывает капсулу,
игрок теряет корабль и груз, но остаётся жив. Вопрос: нужна ли «смерть»,
от которой надо спасаться?

**Форма вопроса:** нужны ли все три в релизе, или какое-то подмножество?

## 27. СИЛА ПРОТИВНИКА: расчёт «новичок против Таргоида»

### 27.1. Принято: все три предмета нужны

> «Все три предмета нужны, даже если пока не определились, как с ними
> поступить».

**E.C.M., энергобомба и побег — все в релиз.** Как именно — решим позже.
Записано в бэклог.

### 27.2. Параметры из blueprint'ов ZX Spectrum

| | Таргоид (`$6C13`) | Cobra Mk III пират (`$64A7`) |
|---|---|---|
| Max energy | **`$F0` = 240** | `$96` = 150 |
| **Laser weighting** | **`$FF` = 255 (максимум)** | `$8C` = 140 |
| Max speed | `$27` = 39 | `$1C` = 28 |
| Bounty | `$01F4` = 500 CR | `$00AF` = 175 CR |
| Тип (`$12`) | `$0C` = Thargoid | `$80` |

У игрока стартовый корабль Cobra Mk III: **максимум энергии 255**
(не 240!), импульсный лазер, урон 15.

### 27.3. Расчёт — и он даёт неожиданный ответ

**Игрок наносит:** 15 урона за выстрел. Темп импульсного с перегревом —
4.55 выстр/сек (раздел 10). **DPS = 68.3.**

**Таргоид восстанавливает** — здесь и находится главное. Разбор `$A2C0`:

```
INC C          ; +1 энергии за кадр
CP $F0         ; если максимум >= $F0...
INC C ×3       ; ...то +4 за кадр, а не +1
...
CP $50         ; если энергия > 80 → throttle = 1
CP $34         ; если энергия < 52 → throttle = 2 (СВОБОДНАЯ регенерация)
SUB $02        ; при throttle = 1: отнять 2
```

**Ключевая деталь:** у Таргоида максимум ровно `$F0`, поэтому он получает
**+4 за кадр**. При энергии ниже 52 (`$34`) тормоз сбрасывается, и он
восстанавливает полные **+4 × 50 кадров = 200 энергии в секунду**.

**Итог:**

| Величина | Значение |
|---|---|
| DPS игрока импульсным | 68.3 |
| Регенерация Таргоида | **200/сек** |
| Чистый урон | **−131.8/сек** |

## Игрок на стартовом корабле с импульсным лазером НЕ МОЖЕТ убить Таргоида.

Не «сложно». Не «маловероятно». **Математически невозможно.**

### 27.4. Почему это не баг, а замысел

Проверка показывает, что так и задумано:

1. **Таргоид — не обычный враг.** `$A3F0` — при разгоне в новую систему
   есть шанс «вызвать подкрепление» именно Таргоидом. Это событие,
   а не рутинная встреча.
2. **Скорость регенерации привязана к максимуму энергии.** Чем крепче
   корабль, тем быстрее он лечится — то есть **толстые корабли
   регенерируют быстрее**, и это делает их принципиально другими целями.
3. **Bounty 500 CR** — самая высокая награда среди обычных кораблей
   (Cobra Mk III — 175 CR). За такую награду и бой должен быть особым.
4. **`laser weighting $FF`** — Таргоид стреляет практически непрерывно
   (100% шанс за кадр для новичка, 50% для Dangerous+).

### 27.5. Что нужно, чтобы убить Таргоида

**Вариант 1: военный лазер.** Урон 23, DPS = 23 × 6.30 = **144.9**.
Против регенерации 200 — **всё ещё меньше!** Не хватает.

**Вариант 2: военный лазер + снижение энергии.** Если держать Таргоида
в верхнем диапазоне (>80), тормоз throttle = 1 и регенерация падает до
**+2 за кадр = 100/сек**. 144.9 > 100 → **можно убить**, чистый урон
44.9/сек, время убийства 240 / 44.9 = **5.3 секунды** непрерывного огня.

**Вариант 3: энергобомба.** Одноразовая, уничтожает **всех**. Именно
поэтому она существует — это ответ на ситуации, где обычное оружие
бессильно.

**Вариант 4: не связываться.** Скорость Таргоида 39 против 28 у Cobra.
Он **быстрее**. Убежать сложно.

### 27.6. Ответ на вопрос пользователя

**Шанс у опытного игрока на начальном корабле с начальным оружием
против Таргоида — ноль.** Не «низкий», а именно нулевой: математика
не позволяет нанести достаточно урона, пока Таргоид восстанавливается
быстрее, чем игрок бьёт.

**Это сильное открытие для дизайна:**

- у нас появляется **настоящий «не тот враг»** — событие, которое надо
  распознать и **не вступать в бой**, а уходить или применять особое
  средство;
- это оправдывает существование **энергобомбы** (27.5, вариант 3);
- это делает **прокачку оружия осмысленной**: без военного лазера
  Таргоид недосягаем;
- и это хороший аргумент в пользу **предупреждения**: игрок должен
  понимать, что перед ним, **до** боя (силуэт, тип корабля).

### 27.7. Для нашей модели (не для оригинала)

Наша система боя ещё не написана, поэтому это **не обязательно**
повторять один в один. Но принцип стоит взять:

**должен существовать враг, которого нельзя победить текущим оружием.**
Иначе прогрессия оружия бессмысленна, и любой бой сводится к «сколько
времени жать кнопку».

### 27.8. Оговорка о точности расчёта

Расчёт опирается на:
- урон лазера `$B692` (15 / 23 / 50) — **точно из кода**;
- темп огня 4.55 / 6.30 выстр/сек — **из раздела 10**, проверено тестами;
- регенерацию `$A2C0` — **точно из кода**;
- максимум энергии Таргоида `$F0` — **точно из blueprint'а**.

**Чего нет:** урона вражеского лазера по игроку. В коде этот путь не
найден прямо; вероятно, он в неразобранном участке. Поэтому «сколько
секунд продержится игрок» — **не рассчитано**.

## 28. ПОЛНЫЙ РАСЧЁТ БОЯ: все корабли, без промахов

### 28.1. Принятые допущения

1. **Игрок не промахивается** — весь урон доходит.
2. **Регенерация врага — по худшему для игрока случаю** (свободная,
   `throttle = 2`, при энергии ниже 52): `+4/кадр` для кораблей с
   максимумом ≥ `$F0`, иначе `+1/кадр`.
3. **Темп огня — из раздела 10** (с перегревом):
   импульсный 4.55, луч 6.30, военный 6.30, добывающий 0.98 выстр/сек.
4. **Урон:** 15 / 15 / 23 / 50.
5. **50 кадров в секунду.**

→ DPS: импульсный **68.3**, луч **94.5**, военный **144.9**, добывающий **49**.

### 28.2. Сила корабля определяется ОДНИМ порогом

(`$A2C0`: `CP $F0` → `+4`, иначе `+1`). Отсюда всего **два класса**:

| Класс | Условие | Регенерация |
|---|---|---|
| **Обычный** | max energy < 240 | **50/сек** |
| **Тяжёлый** | max energy ≥ 240 | **200/сек** |

Порог `$F0` = 240 — это **и есть** граница «можно убить / нельзя».

**Это хороший дизайн-урок:** самый опасный враг — не тот, кто страшно
выглядит, а тот, кого не получается убить, пока он методично стреляет.

### 28.7. Оговорки

- **Урон вражеского лазера по игроку не найден** в коде. Поэтому
  «сколько секунд продержится игрок» — не рассчитано. Все цифры выше
  описывают **скорость убийства врага**, не продолжительность боя.
- Модель регенерации взята в «худшем для игрока» варианте. В реальности
  при энергии выше 80 работает тормоз (`throttle = 1`), и регенерация
  падает вдвое — то есть **убить проще**, если держать врага «сытым».
  Но без промахов это не влияет на вывод: класс определяется максимумом.
- `Coriolis` имеет энергию 240, но это станция — её нельзя атаковать
  в нашей модели.

## 29. УРОН ПО ИГРОКУ: почему его нет в коде

### 29.1. Результат поиска: НЕ НАЙДЕН — и это не упущение

Искал по всему `elite.skool` (15822 строк кода):
- `fore_shield`, `aft_shield`, `SHIELD` — **0 совпадений**;
- `energy` у игрока — **нет такого поля вообще**;
- `damage to the player`, `player is hit` — **0**;
- поля `$D0B7`–`$D0BC` — там **другое** (флаги экрана/демо, курсор).

**Вывод: в ZX Spectrum-версии у игрока нет ни щитов, ни энергии.**

### 29.2. Что есть вместо этого

Проверка показывает, что **вражеский лазер только рисуется**:

`$A878` (в процедуре отрисовки корабля):
```
BIT 3,(IX+$20)   ; должен ли этот корабль стрелять?
RET Z
LD A,(IY+$14)    ; точка пушки
CALL $AE50
LD C,A
; ... рисуем линию через $B044 (клиппинг + отрисовка отрезка)
RES 3,(IX+$20)   ; сбросить флаг
RET
```

`$B044` — routine клиппинга и отрисовки линии. **Никакой проверки попадания,
никакого вычитания энергии.** Луч рисуется и исчезает.

### 29.3. Что тогда убивает игрока

**Столкновение.** `$B4D8` (`check_ship_contact`):

```
; проверка попадания корабля в габарит игрока
LD L,(IX+$00) / H,(IX+$01)   ; x корабля
SBC HL,DE                     ; против порога
RET NC                        ; не попал — выйти
... то же для y и z
LD A,(IX+$08)
ADD A,A
RET NZ                        ; ...
```

Если попало — корабль **уничтожается** (`$B5A8`: обнулить его энергию),
а игрок получает **не урон, а последствия**: тряску экрана, звук, возможно
потерю груза через `$D1E9`.

**То есть: столкновение убивает врага, а не игрока** — но игрок при этом
теряет груз и оборудование.

### 29.4. Тогда как игрок вообще погибает?

Через **«GAME OVER»** (`$7521`), но он вызывается **не из боя**:

`$7538`: 30 раз рисуется «GAME OVER» поверх звёздного поля, затем
`$7569` — пауза 50 кадров, `$7575` — **`JP $739E` («Show another demo ship»)**.

**Это титульная заставка, а не смерть в бою.** То есть в Spectrum-версии
«смерть» реализована как возврат к демо-экрану, и запускается она из
другого места, не из обычного боя.

### 29.5. Что это значит — честный вывод

**В ZX Spectrum-версии игрок практически неуязвим в бою.** Вражеские лазеры
создают визуальный шум и, вероятно, влияют на что-то ещё (например, через
`$9CA3`/`$9CA4` — счётчики сообщений), но **прямого вычитания энергии/щитов
в разобранном коде нет**.

**Возможные объяснения:**

1. **Код не полностью размечен.** Дизассемблер — работа в процессе
   (README: «The aim is to comment each routine»). Часть кода может быть
   не размечена и не найдена поиском по комментариям.
2. **Урон идёт через неразобранный участок** — например, через `$B044`
   (клиппинг), где может быть проверка пересечения с центром экрана.
3. **Это упрощение Spectrum-порта.** 48K — жёсткое ограничение по памяти.
   Возможно, разработчики пожертвовали системой щитов.

### 29.6. Что это значит для расчётов (разделы 27–28)

**Все расчёты «время убийства» остаются верными** — они описывают,
сколько нужно бить врага. Это подтверждено кодом.

**Но «сколько продержится игрок» посчитать НЕЛЬЗЯ** — не потому, что
сложно, а потому что **в этой версии такого параметра нет**.

**Для нашей модели это освобождает руки:**
- можно **не ограничивать** длительность боя «здоровьем игрока»;
- риск игрока выражается **потерей груза и оборудования** (`$D1E9`), а не
  смертью;
- появляется естественное объяснение, **почему капсула нужна**: это
  единственная «страховка», потому что обычной смерти нет.

**Это хорошо ложится на idle:** игрок не «умирает», он **теряет добро**.

### 29.7. Оговорка

Если пользователь хочет точное воспроизведение **BBC-версии** — там щиты
и энергия есть (`fore_shield`/`aft_shield` в BBC-исходниках), и расчёт
продолжительности боя возможен. Но мы работаем по Spectrum, где этого нет.

**Решение за пользователем:** считать Spectrum эталоном (нет здоровья
игрока) или добавлять здоровье своей моделью.

## 30. ЭНЕРГОБЛОКИ: найден механизм (исправление раздела 29)

### 30.1. Пользователь был прав, агент ошибся

Пользователь: «В ZX Spectrum корабль игрока оснащён энергетическими блоками.
Урон расходует энергию; когда она исчерпана — корабль уничтожается.
Energy Unit удваивает скорость восстановления энергоблоков».

**Проверка кода подтверждает всё три утверждения.**

Ошибка раздела 29 была в том, что агент искал слова `shield` и `energy`
и не нашёл поля с такими именами. **Но механизм есть — он называется
«бар-гейджи» (bar gauges), а не «энергия».**

### 30.2. Что такое бар 1 и бар 2

`$70E8` — **dashboard bar 1**, `$70EA` — **dashboard bar 2**. Это и есть
энергоблоки (в BBC-версии им соответствуют fore/aft shield).

`$9946` (`reset_tracking_state`) при сбросе ставит обоим **`$A0` = 160** —
максимальное значение.

### 30.3. Как энергия тратится

`$9A40` (вызывается каждый кадр во время стыковки):

```
$9A6E LD HL,$70E8     ; бар 1
$9A71 LD A,($9CA3)    ; ← "дренаж" из таймера сообщений
$9A74 CALL $9AA7      ; вычесть

$9A77 LD HL,$70EA     ; бар 2
$9A7A LD A,($9CA4)    ; ← второй "дренаж"
$9A7D CALL $9AA7      ; вычесть
```

**`$9CA3` и `$9CA4` — это величина урона.** Они заполняются боевым ИИ
(`$A67D`, `$A674`) — то есть попадание врага увеличивает счётчик,
а счётчик вычитается из полосы.

`$9AA7` (`step_or_refill_bar_gauge`) — вычитает A из баров, и **если A ≥ `$46`
(70), бросает `$D0F3`/`$D1E9` — тот самый бросок на повреждения груза
и оборудования.** Это связывает «энергия» и «потеря добра».

### 30.4. Как энергия восстанавливается

`$9ADB` (`nudge_tracked_object_timers`) — подтягивает бары к `$A0` (160).
**И вот Energy Unit:**

```
c$9ADB LD A,($D08B)      ; Energy Unit установлен?
       AND A
       CALL NZ,$9AE2     ; ← если ДА, выполнить процедуру ЕЩЁ РАЗ
*$9AE2 LD HL,$70FC          ; обычный ход
```

**Energy Unit = удвоение скорости восстановления.** Буквально: рутина
вызывается дважды. Ровно как сказал пользователь.

### 30.5. Что ещё расходует энергию

`$9CA2` — счётчик, который **увеличивается каждой стрельбой игрока**
(`$B686` в `fire_player_laser`) и **каждым выстрелом E.C.M.** (`$B824`).

В `$9A84`:
```
LD A,($D041)   ; идёт экранная вспышка?
AND A
LD A,($9CA2)
JR Z,$9A8A
INC A          ; если вспышка — +1
*$9A8A LD C,A
```

**То есть стрельба тоже жжёт энергоблоки** — прямая связь «стрелял →
просел по энергии». Это в точности принцип BBC-версии (лазеры едят
энергию), только реализованный через счётчик.

### 30.6. Что происходит при нуле

Бары доходят до 0 → следующий шаг пытается вычесть из нуля → ветка
`$9A92` обнаруживает underflow → **устанавливает `$711F`** — «последовательность
завершена / цель слишком близко».

`$711F` — тот самый флаг, который:
- в `$B4D8` (`check_ship_contact`) **сразу выключает проверку столкновений**;
- в `$A6DF` отключает рисование прицела;
- при отправке `$B5D3` (`INC A / LD ($711F),A`) — запускает переход
  к «GAME OVER».

**То есть ноль энергии = конец.** Подтверждено.

### 30.7. Исправленный вывод

| Утверждение | Статус |
|---|---|
| У игрока есть энергоблоки | ✅ **подтверждено** (бары 1–2, `$70E8`/`$70EA`) |
| Максимум | ✅ **`$A0` = 160** каждому, итого 320 |
| Урон расходует энергию | ✅ **подтверждено** (`$9CA3`/`$9CA4` → `$9AA7`) |
| При нуле корабль гибнет | ✅ **подтверждено** (`$711F` → GAME OVER) |
| Energy Unit удваивает восстановление | ✅ **подтверждено** (`$9ADB`, повторный вызов) |
| Стрельба тоже жжёт энергию | ✅ **найдено** (`$9CA2` в `$B63C`) |

**Раздел 29 был неверен. Пользователь прав.**

### 30.8. Почему агент ошибся — и что с этим делать

Агент искал **имена** (`shield`, `energy`) вместо **механизма**. В Spectrum
дизассемблере поля названы `dashboard bar 1/2`, потому что автор разметки
описывал их как индикаторы панели, а не как здоровье.

**Урок:** в дизассемблере искать надо **по поведению** (кто вычитает, кто
прибавляет, что происходит при нуле), а не по ожидаемым словам.

### 30.9. Что это меняет в расчётах

**Теперь можно посчитать живучесть.** Нужны:
- 320 единиц энергии (2 × 160);
- скорость восстановления баров — 1 тик за кадр на бар (плюс удвоение
  при Energy Unit);
- величина урона за попадание — `$9CA3`/`$9CA4`.

**Урон за попадание искать надо** — это последняя недостающая цифра.
Она заполняется в `$A67D`/`$A674`. Это следующий шаг.

## 31. УРОН ЗА ПОПАДАНИЕ: найден — но картина сложнее, чем казалось

### 31.1. Найдено: урон = 7, ФИКСИРОВАННЫЙ для всех кораблей

`$A661`–`$A685` (в конце `$A587`, боевой ИИ):

```
$A65D SET 3,(IX+$20)   ; выстрелить
$A661 LD A,D           ; дистанция
$A662 CP $04
$A664 JR C,$A669
$A666 SLA H            ; повернуть проверку
$A668 RET NC
*$A669 LD HL,$7128
$A66C SET 6,(HL)       ; звук
$A66E BIT 7,(IX+$08)   ; ← ЗДЕСЬ выбор бара
$A672 JR Z,$A67D
$A674 LD A,($9CA4)     ; бар 2 (корма)
$A677 ADD A,$07        ; ← УРОН 7
$A679 LD ($9CA4),A
$A67C RET
*$A67D LD A,($9CA3)    ; бар 1 (нос)
$A680 ADD A,$07        ; ← УРОН 7
$A682 LD ($9CA3),A
```

**Урон фиксированный: `$07` = 7. Для всех кораблей одинаковый.**

### 31.2. Пользователь был прав про «класс мощности», но его нет

Пользователь предполагал: «у каждого корабля свой Laser Power (у Viper — 2)».

**Проверка: в Spectrum такой таблицы НЕТ.** Урон в `$A677`/`$A680`
**захардкожен как `ADD A,$07`** — одно и то же число для Sidewinder,
Thargoid и любого другого.

**Что отличает корабли — не сила удара, а вероятнось выстрела**
(`blueprint $02`), разобранная в разделе 28. То есть:

| Параметр | Есть? | Где |
|---|---|---|
| Сила удара | ❌ нет, у всех 7 | `$A677`/`$A680` |
| Шанс выстрела | ✅ есть, разный | blueprint `$02` |
| Нос / корма | ✅ есть | `BIT 7,(IX+$08)` → бар 1 или бар 2 |

**Разделение на два бара по «нос/корма»** — это аналог fore/aft shield
из BBC. Урон идёт в зависимости от того, откуда стреляют.

### 31.3. ГЛАВНАЯ НАХОДКА: энергоблоки работают только при стыковке

Здесь агент допустил ошибку в разделе 30, и её надо исправить.

`$9A59` — рутина, вычитающая урон из баров (`$70E8`/`$70EA`):

> **Ничего не делает, пока не установлен флаг `$7104`**
> (**идёт стыковочная последовательность**). Пока он установлен —
> подтягивает таймеры (`$9ADB`) и **сливает бары 1 и 2 к целям по
> таймерам `$9CA3`/`$9CA4`**.

```
*$9A59 LD HL,$7104      ; флаг стыковки
       XOR A
       CP (HL)
       RET Z            ; ← нет стыковки — ВЫХОД, ничего не делаем
```

**То есть бары 1 и 2 расходуются и восстанавливаются ВО ВРЕМЯ СТЫКОВКИ,
а не в бою.**

Аналогично `$9ADB` (восстановление, `+1` за кадр, ×2 с Energy Unit)
вызывается **только из `$9A59`** — то есть тоже только при стыковке.

### 31.4. Что это значит

**Раздел 30 был частично неверен.** Я нашёл верные адреса, но сделал
неверный вывод: решил, что это «здоровье в бою». В действительности:

- **бары 1 и 2 — это энергия на манёвр стыковки**, а не боевой щит;
- **Energy Unit ускоряет восстановление в доке**, а не в бою;
- **`$9CA3`/`$9CA4` заполняются боевым ИИ** (`$A67D`/`$A674`), но
  расходуются **только когда идёт стыковка**.

**Это контринтуитивно, но объяснимо:** в 48K-версии экономили место.
Вместо отдельной системы щитов разработчики переиспользовали те же
полосы для «энергии захода на стыковку» — и урон, накопленный в бою,
**проявляется при стыковке**: чем больше по тебе стреляли, тем меньше
энергии на манёвр.

**И это идеально объясняет `$D1E9`:** большой шаг (много накопленного
урона) → бросок на повреждения груза/оборудования. То есть **избитый
в бою корабль плохо стыкуется и теряет добро.**

### 31.5. Что это даёт для нашей модели — и это отличная находка

**Связка, которую даёт оригинал:**

```
бой → накопленный урон копится в $9CA3/$9CA4
      ↓
стыковка → расходует бары 1 и 2, величина шага = накопленный урон
      ↓
большой шаг (≥ $46 = 70) → бросок $D1E9 → потеря груза/оборудования
```

**То есть урон в бою не убивает — он портит стыковку.** Ты не умираешь,
ты **прилетаешь избитым и расплачиваешься добром**.

Для idle это **идеальная механика**:
- нет «смерти» в бою насовсем;
- но есть накопительный ущерб с отложенным последствием;
- игрок видит, что бой был плохим, **на стыковке** — не сразу.

### 31.6. Что осталось неясным

1. **Как сбрасываются `$9CA3`/`$9CA4`?** `$9CBB` обнуляет все три
   (`$9CA2`–`$9CA4`) в начале прохода ИИ — надо проверить, каждый ли кадр.
   Если каждый кадр, то накопления нет и механика другая.
2. **Что происходит при нуле баров** — `$711F` устанавливается, но
   `$711F` уже означает «стыковочная последовательность завершена».
   Возможно, «энергия кончилась» = «стыковка провалена», а не «смерть».

**Это надо добить — без этого вывод 31.5 под вопросом.**

## 32. ВТОРОЙ ИСТОЧНИК: `ataribaby42/zx-elite` — всё подтверждено

Пользователь предложил проверить второй репозиторий. **Это решающий шаг.**
Склонирован в `reference/zx-elite-ataribaby` (в `.gitignore`).

### 32.1. Что это за проект

`ataribaby42/zx-elite` — **реконструкция исходников**, а не просто дизассемблер:

> «This project reconstructs the supplied original ZX Spectrum Elite 128K-compatible
> release as an independent, standalone project. **The default TAP is byte-for-byte
> identical** to `assets/Elite - 128k.tap`.»

Есть `verify.bat`, который проверяет побайтовое совпадение с оригинальной
лентой. То есть **сборка воспроизводит оригинал**, а не является догадкой.

**Важное открытие:** «Elite 128K — не 128K-игра». Это оригинальная 48K-игра
с исправлением несовместимости на 128K-машинах. Банков памяти нет,
отдельного 128K-кода нет.

**Следствие:** миссии Constrictor и Thargoid Documents, о которых шла речь
в разделах 12–13, **не в этой версии**. Они в переиздании 1993 года
(«Elite 3»). Это ещё одна версия — уже третья.

### 32.2. ГЛАВНОЕ: у игрока есть щиты И энергоблоки

Аннотации второго источника (с пометкой **VERIFIED**) прямо называют поля:

| Адрес | Имя | Описание |
|---|---|---|
| `$7046` | **ForwardShield** | носовой щит, 0..160, полоса FS |
| `$7048` | **AftShield** | кормовой щит, 0..160, полоса AS |
| `$7054` | **EnergyBank1** | энергоблок 1 из 4, 0..160 |
| `$7056` | **EnergyBank2** | энергоблок 2 |
| `$7058` | **EnergyBank3** | энергоблок 3 (нужен ≥ `$28` для невидимости) |
| `$705A` | **EnergyBank4** | энергоблок 4; ниже `$A0` → тревога |
| `$704C` | **CabinTemperature** | CT |
| `$704E` | **LaserTemperature** | LT |
| `$7050` | **AltitudeGauge** | AL |
| `$7052` | **SpeedGauge** | SP |

**Итого запас игрока: 4 × 160 + 2 × 160 = 960 единиц.**

### 32.3. Где я ошибался — и где был прав

**Ошибка (раздел 30–31):** я смотрел на `$70E8`/`$70EA` и думал, что это
два энергоблока. **На самом деле это не энергия вообще** — в реконструкции
эти адреса попадают совсем в другую область (там `StationPresent`,
`DockingComputerFitted`, `FlightCondition`, `DockingComputerFlag`).

**Причина путаницы:** два дизассемблера адресуют **разные версии**.
Rasmus-M разбирает одну, ataribaby42 — другую («128K-compatible», тоже 48K-код,
но иная сборка). Адреса не совпадают.

**Прав (раздел 27–28):** расчёты времени убийства врагов — они опирались
на blueprint'ы (`max energy`, `laser weighting`), а они одинаковы в обеих
версиях. **Все таблицы разделов 27–28 остаются в силе.**

### 32.4. Механика энергии — точно

`UpdateEnergyAndShields` (`$A572`), каждый кадр полёта:

1. **если в доке (`FlightCondition = 0`) — выход**, ничего не делается;
2. **EnergyBank4 < `$A0`** → `FlightCondition = $63` (мигающая тревога);
3. **`RechargeEnergyBanks`** — восстановление;
4. **`ApplyShieldDamage`** для носа (`FrontDamageThisUpdate`) и кормы
   (`RearDamageThisUpdate`);
5. **`DrainEnergyBanks`** — расход `EnergyDrainThisUpdate` **четыре раза**
   (`LD B,$04`).

### 32.5. Урон: 7 за попадание, подтверждено независимо

`L_FAF0`:
```
L_FAF0 LD A,(FrontDamageThisUpdate)
       ADD A,$07              ; ← +7
       LD (FrontDamageThisUpdate),A
```
`L_FADC`: то же для `RearDamageThisUpdate` при `z < 0` (корабль сзади).

**Совпадает с `$A677`/`$A680` из первого дизассемблера. Два независимых
источника дают одно число: 7.**

**Важное уточнение:** выстрел идёт **не всегда в попадание**. `L_FADC`:
попадание — если `range < 4`; иначе нужен `|H| ≥ 96` (точное прицеливание),
иначе **промах**. То есть не каждый выстрел врага — урон.

### 32.6. Порядок расхода: щит → энергоблоки → смерть

`ApplyShieldDamage` (`$A5C0`) — точная механика:

```
если урон = 0: DamageCounter -= 1 (не ниже 0), выход
если урон >= $46 (70): СНАЧАЛА DamageEquipmentOrCargo (потеря груза/оборудования)
затем щит теряет урон до 5 раз
если щит не может заплатить → щит = 0,
   остаток уходит в энергоблоки (DrainEnergyBanks),
   DamageCounter += 5; при >= 13 — снова DamageEquipmentOrCargo
```

`DrainEnergyBanks`: если **все четыре банка пусты** → `PlayerDeadFlag = 1`,
**игра заканчивается**.

**То есть: щит — буфер, энергоблоки — запас жизни, ноль банков — смерть.**
Пользователь был прав полностью.

### 32.7. Восстановление и Energy Unit

`RechargeEnergyBanks` (`$A63A`):
```
LD A,(EnergyUnitFitted)
AND A
CALL NZ,RechargeStep    ; ← если Energy Unit есть — ВТОРОЙ шаг
```
`RechargeStep`: `+1` в первый неполный банк, **сканируя от bank4 вниз**.
Когда все 4 полны — `+1` в щиты.

**Energy Unit = двойной шаг = 50 → 100 единиц/сек. Подтверждено.**

### 32.8. Стрельба жжёт энергию — и цифра иная, чем я считал

`$EC11` (`L_EC11`): **+1 к `EnergyDrainThisUpdate` за каждый выстрел лазера**.
`$EDA9`: то же, пока идёт E.C.M.

А в `$A59D` этот расход берётся **четыре раза** (`LD B,$04`).

**Один выстрел лазера = 4 единицы из банков.**

Pulse 4.55 выстр/сек × 4 = **18.2 единицы/сек расхода**.
Восстановление 50/сек **обгоняет** — то есть стрельба сама себя окупает,
но не мгновенно: на серии выстрелов банки проседают.

## 33. ИДЕЯ В БЭКЛОГ: пройденный путь на карте галактики

**Запрос пользователя:** отображать пройденный путь на карте галактики.

**Зачем это нужно.** Сейчас карта (`drawMap()` в `src/ui/main.ts`) показывает
системы, но **не историю**. Игрок не видит, откуда пришёл и куда ходил.
В оригинале такого тоже нет — но в idle это **сильный элемент**:
карта становится **летописью**, а не справочником.

**Почему это особенно хорошо для idle:**
- игрок уходит и возвращается — видит, **сколько успел**;
- путь рисует «маршрут», который сам по себе награда (как в стратегиях);
- не требует присутствия, но даёт ощущение прогресса.

**Что нужно для реализации (когда дойдёт очередь):**
- `state` уже знает `galaxy` и `system`, но **не хранит историю**;
- нужен массив посещений: `{galaxy, system, timestamp}`;
- `drawMap()` дополнить отрисовкой линий между последовательными точками;
- решить: хранить **всю** историю или только последние N прыжков
  (иначе на тысячах прыжков карта станет мусором);
- решить: показывать путь **только текущей галактики** или межгалактические
  переходы тоже.

**Статус:** идея принята в бэклог, реализация отложена (ядро не трогаем,
раздел 23.4).

### 34.5. Что рекомендует агент

**Ключевой вопрос — не цифры, а форма боя.** Все расчёты выше описывают
**оригинал**, а не нашу игру. Прежде чем переносить числа, надо решить,
**какой бой мы делаем**.

Три варианта, и они очень разные:

**A. Бой как в оригинале, но пошаговый.** Раунд = тик. У игрока щиты
и банки, у врага — энергия и шанс выстрела. Числа берём из оригинала.
Плюс: честно. Минус: много состояния, сложно в UI.

**B. Бой как «одно решение».** Игрок выбирает: драться / бежать / капсула.
Драка разрешается броском с вероятностью, выведенной из наших расчётов
(Sidewinder — легко, Thargoid — невозможно). Плюс: дёшево, идеально для
idle. Минус: нет тактики.

**C. Бой как мини-игра (как стыковка).** Отдельный прототип, где есть
ощущение схватки. Плюс: интересно. Минус: работа.

**Агент склоняется к B для MVP и C для релиза** — потому что все цифры
уже посчитаны, и B из них получается почти бесплатно.
